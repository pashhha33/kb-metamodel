## Карточки решений

### D-0042…D-0046: сценарий «Глава» принят (ADR-0010)
- **Дата:** 2026-10-21
- **Контекст:** пользователь выбрал Q-33 = B, Q-34 = C, Q-35 = «по рекомендации» (A + C), Q-36 = A.
- **Главный принцип (D-0042):** метамодель **не знает о кнопках**. Она объявляет «тип является упорядоченной последовательностью внутри родителя» парой полей, а плагин обслуживает любое такое объявление. Это сохраняет S1 («метамодель как данные») и E3 («всё как знание») и даёт бесплатное переиспользование для `Episode`/`Series`, `Track`/`Album`, `Task`/`Project`.
- **Отклонено:** типы `Sequence` (дублировал бы пару полей на `ObjectType`) и `Form` (дублировал бы данные типа и свойств). Форма создания **выводится**: effective properties (алгоритм ADR-0008 §3.3) ∩ `Automation.form_fields`, порядок, обязательность, контрол по `value_type`, кандидаты по `target_types`/`target_facet`.
- **Новое для модели:** `unique_within` — **первое межобъектное ограничение**. Все 94 предыдущих правила проверяли один объект или разрешение ссылки. Реализация требует индекса «значение области → объекты», поддерживаемого по событиям файлового API.
- **Осознанная потеря:** в Live Preview кнопок в теле заметки в MVP не будет — только в режиме чтения и в панели плагина. CM6-виджеты перенесены на этап 2 фазы 5 как самый хрупкий механизм.
- **Каталог валидации:** 94 → **104 правила** (добавлены `sequence.r1…r6`, `unique.r1…r2`, `meta.r14…r15`).
- **Артефакты:** `ADR-0010`, `03_chapter_scenario.md` (→ `actual`), `RULES.md` §13, `NAME_MAPPING.md`, `00_overview.md` §3.

### D-0057…D-0060: шаг 7 — расслоение документов, закрыт весь реестр диагноза
- **Дата:** 2026-10-21
- **Контекст:** пользователь подтвердил выполнение шага 7. Оставались 6 позиций диагноза: C-04, C-05 (недействительные ID в примерах черновиков), C-36 (реализация внутри документа метамодели), C-37 (тип `документация`), C-38 (статусы документов), C-41 (версии).
- **D-0057 — правило расслоения L-1…L-4.** Стало нормативным, а не описательным: в `docs/metamodel/**` запрещены имена классов и точки API, в `docs/plugin/**` не переопределяется семантика. Проверка — grep в CI (фаза 5). Создан `docs/plugin/ARCHITECTURE.md`, куда перенесены разделы 10, 11, 15, 17, 18 черновика v1.1 и все наши решения по реализации. Раздел 17 v1.1 (13 адаптеров подмены отображения) перенесён в секцию «Отклонено».
- **D-0059 — `inbox/` остаётся read-only.** Соблазн исправить статусы прямо в черновиках отклонён: сырьё должно оставаться снимком исходного состояния, иначе теряется возможность аудита «что было → что стало». Авторитетные статусы ведёт отдельный реестр. Установлен приоритет источников: **ADR > сводное описание > правила > черновики**.
- **D-0058 — C-04 и C-05 закрыты структурно.** Примеры в черновиках содержат один ID для разных объектов (`OBJECT-TYPE-000001` = «Книга» и «Человек») и один ID для двух документов (`DOC-000002`). Исправление примеров не устранило бы причину: последовательный счётчик требует централизованной выдачи. ULID (ADR-0002) снимает причину, а `contract.r3` и `naming.r4…r6` обнаруживают нарушения как ошибки.
- **D-0060 — три независимые версии.** Документа (`version`), метамодели (`metamodel_version`), плагина. В черновике одно поле `версия: 1.1-draft` совмещало первые две.
- **Итог:** реестр диагноза закрыт полностью — **41 из 41**. Дополнительно закрыты 15 пробелов сценариев (G-1…G-15) и 14 требований пользователя (T1…T14).
- **Артефакты:** `docs/plugin/ARCHITECTURE.md`, `docs/metamodel/05_document_status_register.md`, `01_diagnosis.md` (→ 0.2.4).

### D-0049…D-0056: MediaAsset принят (ADR-0011), ядро M1 полное
- **Дата:** 2026-10-21
- **Контекст:** пользователь выбрал Q-41 = A, Q-42 = B, Q-43 = B, Q-44 = A и подтвердил все четыре отклонения от черновика v1.1.
- **D-0052 — решение вопреки рекомендации ассистента.** По Q-42 рекомендовался вариант A (`Gallery.items`, упорядоченный список на стороне галереи). Пользователь выбрал B (`MediaAsset.galleries`, порядок не хранится) с обоснованием: «в галерее порядок изображений не важен, представление будет через Bases, а там много способов сортировки». **Обоснование принято как более сильное:** оно согласовано с двумя уже действующими принципами — ADR-0005 §3.1 (ссылки хранятся только вверх, обратные вычисляются) и ADR-0009 §3.1 (разделение — задача представления, а не хранения). - **D-0055 — расширение ADR-0002 на бинарные файлы.** Конвенция именования прежде описывала только заметки `.md`. Переименование только при создании и по команде: вариант «при каждой правке `title`» означал бы переименование файла и обновление всех ссылок хранилища на каждую правку названия.
- **D-0056 — ядро M1 объявлено полным.** Все 12 типов имеют определённое поведение. Q-32 (заморозка ядра) остался без ответа четвёртый раз, поэтому заморозка принята **по умолчанию** и помечена как предположение, которое можно изменить.
- **Осознанная потеря:** порядок в галерее не сохраняется в данных. Если позже потребуется кураторская подборка с фиксированным порядком, его придётся выражать через `View` либо вводить `Gallery.items` как ломающее изменение.
- **Зафиксированный риск фазы 5:** T8 (изображения в таблицах) невозможен в штатной таблице Bases — только через собственное представление `registerBasesView` (`@since 1.10.0`). Прототип этого представления должен быть **первой** задачей фазы 5.
- **Артефакты:** `ADR-0011`, `04_media_asset_scenario.md` (→ `actual` v0.3.0), `RULES.md` (группа `media.*`, `naming.r11`; итог **114 правил**, пересчитано программно), `00_overview.md` §5.2 и §7.5, `TYPE_PREFIX_REGISTRY.md` (21 префикс), `NAME_MAPPING.md`.

### D-0039…D-0041: жизненный цикл и сценарий «Глава»
- **Дата:** 2026-10-21
- **Контекст:** пользователь выбрал Q-30 = A и Q-31 = B, а на Q-32 (заморозка ядра) ответил не выбором, а первым живым сценарием: `Chapter` привязан к `Book`, нужны номер и имя главы, кнопки перехода по соседям и к родителю, автосоздание отсутствующего соседа с запросом имени, при пропуске имени — «Глава N».
- **D-0039 (архивирование).** Только поле `status`. Обоснование: вариант с папкой `Archive/` дал бы два источника одного факта, а мы этот принцип уже применили трижды (удаление `Taxonomy.facets`, замена плоского `categories`, отклонение варианта C в ADR-0007). Побочный эффект принят осознанно: в проводнике архивные объекты не отделены визуально; компенсация — `View` с фильтром, а не DOM-интеграция (запрещена P-API-1).
- **D-0040 (слияние и миграция).** Два типа отношений вместо одного: слияние N:1 и замена 1:1 имеют разную кардинальность и разные последствия. `duplicate_of` отклонён — это диагноз, а не состояние данных. Введено правило `lifecycle.r1` (запрет цепочек), которое делает разрешение замены O(1).

Ключевой принцип: **метамодель не знает о кнопках**, она объявляет «тип является упорядоченной последовательностью внутри родителя», а плагин обслуживает любое такое объявление. ### D-0017…D-0020: классификация (ADR-0005)
- **Дата:** 2026-10-21
- **Контекст:** три документа задают классификацию несовместимо (3 уровня в «утверждённых» spec/v1.0 против 4 в черновике v1.1); группы spec §5 не имеют статуса; `Персонаж` вне классификации; `Video`/`Film` пересекаются; способ хранения `тип_объекта` в экземпляре не определён.
- **Решения пользователя:** Q-14 = B (6 абстрактных + 8 конкретных), Q-15 = A (`Character` → наследник `Context`), Q-16 = B (оставить оба с критерием различения), Q-17 = A (`type` строкой).
- **Решение:** 4 уровня классификации со ссылками только вверх; поле `is_abstract`; группы spec §5 становятся абстрактными типами; критерий `Source` (источник информации) vs `Work` (самостоятельное произведение); `type` хранится строкой snake_case.
- **Альтернативы:** 3 уровня (не выражает независимые измерения); wikilink в `type` (дублирует `type_prefix` в имени файла, ломает фильтрацию Bases); гибрид «строка + вычисляемый `type_ref`» — отклонён как нарушение принципа «один факт — одно место», только что применённого к `Taxonomy.facets`.
- **Осознанная потеря:** в графе Obsidian нет рёбер «экземпляр → тип». Компенсация — собственное представление иерархии типов в плагине.
- **Артефакты:** `docs/adr/ADR-0005-classification.md`, `docs/metamodel/TYPE_PREFIX_REGISTRY.md`, `docs/metamodel/00_overview.md`.

### D-0016: что берём у Exocortex
- **Дата:** 2026-10-21
- **Контекст:** пользователь предложил обратить внимание на Exocortex (`kitelev/exocortex`, бета, RDF/SPARQL, MIT, 11 400+ тестов), где в режиме Source видны ключи, а в режиме View — другие имена.
- **Берём:** E1 обязательный `label` + отчёт о качестве метамодели; E2 разделение технического и читаемого имени; E3 «всё как данные» (`View`, `Automation` — объекты M1); E4 экспортируемый пакет метамодели как задел.
- **Не берём:** N1 «тройка = файл» (в `exoas-w3c` 31 828 троек → 37 339 файлов — неприемлемо для живой личной БЗ); N2 SPARQL; N3 OWL/SHACL; N4 ExoSync и CLI-parity.
- **Обоснование границы:** Exocortex доказывает работоспособность подхода «метамодель как данные» в Obsidian, но его физическая модель хранения рассчитана на статический корпус онтологий, а не на ежедневное создание связей.
- **Артефакты:** `docs/research/API_FEASIBILITY_NOTES.md` §3.

### D-0014: правило P-API-1 — только публичный API
- **Дата:** 2026-10-21
- **Контекст:** черновик v1.1 §17.5 допускал DOM-интеграцию и внутренние API «при необходимости». Проверка `obsidian.d.ts` показала, что кастомные виджеты свойств и подмена имени файла публично недоступны.
- **Решение:** плагин использует только публичный API. Собственный UI — единственное место отображения `label`. Панель Properties остаётся работающей, но показывает EN-ключи.
- **Альтернативы:** подход MetaEdit 1.9.0 (нативные виджеты свойств через недокументированные механизмы) — отклонён: ломается при обновлениях Obsidian, требует регрессионных тестов на UI.
- **Последствия:** раздел 17 v1.1 выведен из MVP (риск R-07 снят); раздел 18 v1.1 становится основным типизированным вводом.
- **Артефакты:** `docs/research/API_FEASIBILITY_NOTES.md` §2.2, §4.

### D-0012: отмена правила `aliases[0] = название`

### D-0011: привязка свойств — плоский список у типа, defaults у свойства
- **Дата:** 2026-10-21
- **Контекст:** C-20 — главный структурный пробел: связи между `Property` и `ObjectType` нет ни в одном из трёх документов, хотя spec §14 описывает наследование свойств.
- **Решение:** направление «список у типа» (Q3=A) реализовано как гибрид: `ObjectType.properties` — плоский упорядоченный список ссылок; `Property` хранит defaults; `ObjectType.property_overrides` — вложенный список только для ужесточений.
- **Техническое основание:** панель Properties Obsidian не поддерживает вложенные свойства (официальная справка рекомендует source mode), поэтому вложенность изолирована в редко используемом поле.
- **Альтернативы:** B (список у свойства — нельзя переопределить обязательность на тип), C (объект-ассоциация — 200 заметок-связок).
- **Последствия:** `PropertyType` 8 → 6; формат кардинальности унифицирован; правила наследования взяты без изменений из spec §14.
- **Артефакты:** `docs/adr/ADR-0003-property-attachment.md`, `docs/metamodel/NAME_MAPPING.md` §3–4, §7.

### D-0010: идентичность отделена от имени файла
- **Дата:** 2026-10-21
- **Контекст:** три документа задают три несовместимые схемы (C-01…C-03). От выбора зависит объём раздела 17 v1.1.
- **Решение:** `id` = ULID, единственный носитель идентичности. Имя файла `{title} ({type_prefix}-{id}).md`. Разрешение ссылки — по стабильной подстроке `(PREFIX-ULID)`.
- **Альтернативы:** A (только техническое имя — требует 13 адаптеров UI через DOM), B (счётчик — конфликты при синхронизации).
- **Последствия:** раздел 17 выведён из MVP; ссылки правит штатный механизм Obsidian; `title` в имени файла ≤ 60 символов.
- **Артефакты:** `docs/adr/ADR-0002-identity-ulid-and-filename.md`.

### D-0009: три слоя имени — key, label, label_*
- **Дата:** 2026-10-21
- **Контекст:** черновики используют русские ключи, что конфликтует с D-0001.
- **Решение:** технический `key` (EN snake_case) + обязательный `label` (RU) + необязательные `label_*`. Переходный слой RU-алиасов с `warn`.
- **Проверка фактов:** в Bases разделение есть публично (`BasesConfigFile.properties[*].displayName`, `getDisplayName()`, `@since 1.10.0`); в панели Properties — нет; API кастомных виджетов свойств отсутствует.
- **Последствия:** `label` = `rdfs:label` → задел под RDF; автозаполнение `displayName` в `.base`; в панели Properties подписи английские.
- **Артефакты:** `docs/adr/ADR-0001-english-keys-russian-labels.md`, `docs/metamodel/NAME_MAPPING.md`, `docs/research/API_FEASIBILITY_NOTES.md`.
