# ADR-0001: Ключи frontmatter — английские; отображаемые имена — русские, через поле `label`

## 1. Контекст и проблема

Черновики метамодели Second Brain используют русские имена полей: `название`, `тип_объекта`,
`родительский_тип`, `тип_значения`, `кардинальность`, `обязательность`. При этом принятое решение D-0001
требует: документация на русском, идентификаторы и код на английском. Возникает конфликт.

Одновременно пользователь обратил внимание на плагин **Exocortex** (`kitelev/exocortex`), где в режиме
Source видны технические ключи, а в режиме View — человекочитаемые имена. Это указало на недостающий
слой метамодели: **разделение ключа и отображаемого имени**.

Проверка фактов показала:

| Где | Есть ли разделение «ключ / отображаемое имя» | Источник |
|---|---|---|
| Панель Properties Obsidian (редактор) | **Нет.** Переименование свойства меняет ключ во всём хранилище; псевдонимов отображения нет. Nested properties не поддерживаются | `help.obsidian.md/properties` |
| Bases | **Да.** В файле `.base` хранится `properties: { <ключ>: { displayName: string } }`; есть публичный метод `getDisplayName(propertyId)` | `obsidian.d.ts`, `BasesConfigFile.properties`, `@since 1.10.0` |
| Публичный API плагинов для панели Properties | **Нет.** В `obsidian.d.ts` отсутствуют `PropertyWidget`, `registerPropertyWidget`, `MetadataEditor` | проверка `obsidian.d.ts` (306 КБ) |
| Exocortex / RDF | **Да.** Технический IRI + `rdfs:label`; в файловом представлении — UUIDv5 как имя файла + `aliases` как человекочитаемое имя | `kitelev/exoas-w3c` |

Вывод: разделение ключа и подписи — общеотраслевой стандарт (RDF `rdfs:label`), оно поддержано
публичным API Obsidian в Bases, но **не поддержано** в панели Properties. Значит, слой подписей
должен владеть наш плагин.

## 2. Рассматриваемые варианты

| # | Вариант | Плюсы | Минусы | Последствия |
|---|---|---|---|---|
| A | Полностью английские ключи, подпись не моделируется | Просто | В интерфейсе `publisher` вместо «Издательство»; русская документация расходится с данными | Потеря удобства, ради которого черновики были на русском |
| B | Полностью русские ключи | Естественно читается | Нарушает D-0001; кириллица в TS-типах и JSON Schema; проблемы в сторонних инструментах | Технический долг на каждом шаге |
| **C** | **Английский ключ как канон + русский `label` в определении свойства + слой RU-алиасов на переходный период** | Канон машиночитаем; подпись человекочитаема; старые заметки не ломаются сразу; `label` = `rdfs:label` → готовый задел под RDF | Парсер должен понимать оба имени и сообщать о конфликте | Нужен `NAME_MAPPING.md` и правило приоритета при конфликте |

## 3. Решение

**Выбран вариант C.** Устанавливаются три слоя имени:

| Слой | Что это | Пример | Где хранится | Обязательность |
|---|---|---|---|---|
| **`key`** | Технический ключ frontmatter. Только `[a-z0-9_]`, snake_case, ASCII | `publisher` | имя поля в YAML | канон, единственное имя для кода и схем |
| **`label`** | Человекочитаемая подпись по умолчанию | `Издательство` | поле `label` в определении `Property` / `ObjectType` / `RelationType` / `Facet` / `Category` | **обязательное** для всех определений M1 |
| **`label_*`** | Локализованные варианты подписи (задел) | `label_en: Publisher` | то же | необязательное |

Дополнительно вводится **переходный слой RU-алиасов**: плагин при чтении принимает исторические
русские ключи (`название` → `title`, `тип_объекта` → `type`) согласно таблице `docs/metamodel/NAME_MAPPING.md`,
выдаёт диагностику уровня `warn` и предлагает однократную конвертацию. При записи всегда используется
только канонический английский ключ.

**Правило приоритета при конфликте:** если в одном объекте заданы и английский ключ, и его RU-алиас,
значением считается английский; наличие обоих — ошибка уровня `error` с сообщением
«Поле продублировано: `<en>` и `<ru>`. Удалите `<ru>`». Молчаливое слияние запрещено (принцип S6).

**Правило для `aliases`:** поле `aliases` зарезервировано Obsidian для разрешения ссылок
(`parseFrontMatterAliases`, default property). Оно **не используется** для хранения подписей.

## 4. Обоснование

1. **Соответствует D-0001** без потери русскоязычного интерфейса.
2. **`label` — это `rdfs:label`.** Прямое соответствие стандарту, поэтому будущее расширение до RDF/OWL
   не потребует переделки: `Property.key` → локальная часть IRI, `Property.label` → `rdfs:label`.
3. **Подтверждено публичным API Obsidian.** `BasesConfigFile.properties[*].displayName` и
   `getDisplayName(propertyId)` существуют с версии 1.10.0. Наш плагин может записывать `displayName`
   в файлы `.base` автоматически из `label` метамодели — то есть «режим View» с русскими подписями
   работает штатно, без DOM и внутренних API.
4. **Снимает риск R-07.** Потребность в подмене отображения (раздел 17 черновика v1.1) в части свойств
   исчезает: там, где Obsidian не даёт подписей (панель Properties), мы показываем их в собственном UI.
5. **Согласуется с практикой Exocortex**, где технический идентификатор и человекочитаемое имя разнесены
   системно (UUIDv5 + `aliases`), а подписи считаются обязательными — у них есть отдельный
   lint-отчёт по качеству онтологии, проверяющий наличие `label`, `comment`, `domain/range`.

## 5. Последствия

### Положительные
- Один канон для кода, JSON Schema, TS-типов, SPARQL-экспорта.
- Русский интерфейс без русских ключей.
- Автоматическое заполнение `displayName` в Bases.
- Готовый задел под RDF/OWL.

### Отрицательные / стоимость
- Парсер читает два имени вместо одного; нужна диагностика конфликтов.
- Таблица маппинга становится обязательным артефактом, который надо поддерживать.
- В панели Properties Obsidian подписи останутся английскими (публичного API нет). Пользователь sees
  русские подписи в нашей модалке, в наших таблицах и в Bases.

### Что становится возможным позже
- Мультиязычность (`label_en`, `label_de`) без изменения схемы.
- Экспорт в RDF с корректными `rdfs:label`.
- Отключение RU-алиасов одной настройкой, когда хранилище мигрировано.

## 6. Влияние на метамодель

| Элемент | Было | Стало | Тип изменения |
|---|---|---|---|
| Все имена полей | кириллица (`название`, `тип_объекта`) | латиница snake_case (`title`, `type`) | **BREAKING** (rename) |
| `Property.label` | отсутствовало | обязательное поле | additive |
| `Property.definition` | `определение` | `definition` (= `rdfs:comment`) | rename |
| `Property.scope` | `область_применения` + `уровень` (дубль) | одно поле `scope` | **BREAKING** (merge, закрывает C-21) |
| `aliases` | `aliases[0]` дублировал `название` | только реальные псевдонимы | **BREAKING** (отмена правила v1.1 §1.4, см. ADR-0004) |

## 7. Миграция

- Требуется: **да, отложена**.
- Что нужно сделать: однократный проход по хранилищу с переименованием ключей по `NAME_MAPPING.md`.
- Когда: после MVP. До этого работает слой RU-алиасов с `warn`-диагностикой.
- Затронутые файлы: все объекты M0 и все определения M1.
