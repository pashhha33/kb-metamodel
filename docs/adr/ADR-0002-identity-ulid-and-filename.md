# ADR-0002: Идентичность объекта — ULID + имя файла «Title (PREFIX-ULID).md»

## 1. Контекст и проблема

Три документа задают три несовместимых схемы идентичности (противоречия C-01, C-02, C-03):

| Вопрос | Спецификация v1.0 («утверждён») | Метамодель v1.1 (черновик) |
|---|---|---|
| Формат ID | `КОДТИПА-000001`, «возможен ULID или UUID v7» | «основной и единственный — ULID» |
| Имя файла | `Название — ID.md` (название входит, длинное тире) | `{TYPE_PREFIX}-{ID}.md` (название не входит, дефис) |
| Ссылка | `[[Михаил Булгаков — PERSON-000001]]` | `[[PERSON-<ULID>.md\|Михаил Булгаков]]` |

От выбора имени файла напрямую зависит объём самого хрупкого модуля проекта — раздела 17 v1.1
(подмена отображаемого названия в 13 областях интерфейса, частично через DOM и внутренние API).

Проверка публичного API Obsidian (`obsidian.d.ts`):

| Возможность | Есть в публичном API | Сигнатура |
|---|---|---|
| Разрешение ссылки в файл | ✅ | `metadataCache.getFirstLinkpathDest(linkpath, sourcePath): TFile \| null` |
| Обратное преобразование файла в текст ссылки | ✅ | `metadataCache.fileToLinktext(file, sourcePath, omitMdExtension?): string` |
| Генерация ссылки с учётом настроек пользователя | ✅ | `fileManager.generateMarkdownLink(file, sourcePath, subpath?, alias?): string` |
| Атомарная правка frontmatter | ✅ | `fileManager.processFrontMatter(file, fn, options?)` |
| Чтение ссылок из frontmatter | ✅ | `CachedMetadata.frontmatterLinks: FrontmatterLinkCache[]` (с полем `key`) |
| Псевдонимы из frontmatter | ✅ | `parseFrontMatterAliases(frontmatter)` |
| Подмена имени файла в проводнике / вкладках | ❌ | отсутствует |

Вывод: механизм ссылок и разрешения имён доступен полностью через публичный API. Подмена отображения
имени файла — нет. Значит, выгоднее выбрать такую схему имени файла, при которой подмена не нужна.

## 2. Рассматриваемые варианты

| # | Вариант | Плюсы | Минусы | Последствия |
|---|---|---|---|---|
| A | ULID + `{PREFIX}-{ULID}.md` (чистый v1.1) | Имя файла вечно стабильно; ссылки не ломаются никогда | Проводник нечитаем; **требуется весь раздел 17** — 13 адаптеров, DOM, внутренние API, матрица совместимости | Самый рискованный путь для новичка в Obsidian API |
| B | Счётчик + `Название — PREFIX-000001.md` (чистый spec) | Проводник читаем; адаптеры не нужны | Нужен центральный счётчик (конфликты при синхронизации между устройствами); переименование = правка всех ссылок; длинное тире легко опечатать; ID зависит от порядка создания | Риск рассинхрона ID при работе с нескольких устройств |
| **C** | **ULID + `Название (PREFIX-ULID).md`** | Проводник читаем → раздел 17 сокращается до 1–2 областей; ID стабилен и не зависит от названия; при переименовании файла Obsidian штатно правит ссылки; ULID генерируется локально без счётчика | Имя файла меняется при переименовании объекта; скобки в имени файла | Требуется дисциплина: идентичность — это `id` во frontmatter, а не имя файла |

## 3. Решение

**Выбран вариант C.** Устанавливается:

1. **Идентификатор.** `id` — ULID (26 символов, Crockford Base32, лексикографически сортируем по времени
   создания, генерируется локально без сети). UUID v7 не используется. `id` — **единственный** носитель
   идентичности; он хранится во frontmatter и никогда не меняется.
2. **Префикс типа.** Каждому `ObjectType` назначается `type_prefix` — ASCII, `[A-Z][A-Z0-9]*`, уникальный
   в реестре. Реестр ведётся в `docs/metamodel/TYPE_PREFIX_REGISTRY.md`. Сравнение префиксов —
   по точному совпадению всей строки до разделителя, а не по началу строки (закрывает C-08:
   `PROP` и `PTYPE` не конфликтуют, `PROPERTY` и `PROPERTY-TYPE` больше не используются).
3. **Имя файла.** `{title} ({type_prefix}-{id}).md`. Круглые скобки, один пробел перед ними.
   Квадратные скобки запрещены (конфликтуют с wikilink). Длинное тире не используется.
4. **Каноническая ссылка.** `[[{title} ({type_prefix}-{id})|{title}]]`, формируется через
   `fileManager.generateMarkdownLink()`, чтобы уважать настройки пользователя
   («Shortest path when possible» / «Relative path» / «Always include .md»).
5. **Разрешение ссылки.** Всегда по стабильной части — подстроке `({type_prefix}-{id})`, а не по
   отображаемому названию. Одинаковые `title` у разных объектов допустимы и не влияют на разрешение.
6. **Переименование объекта.** Меняются `title` и имя файла. `id`, `type_prefix` и идентичность не меняются.
   Ссылки обновляет штатный механизм Obsidian; плагин дополнительно нормализует alias управляемых ссылок.

**Пример:**

```text
id:        01J8Z6M4K2Q7V9X3N5B0C1D2EF
title:     Михаил Булгаков
type:      person
файл:      Михаил Булгаков (PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF).md
ссылка:    [[Михаил Булгаков (PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF)|Михаил Булгаков]]
разрешение по подстроке: (PERSON-01J8Z6M4K2Q7V9X3N5B0C1D2EF)
```

## 4. Обоснование

1. **Идентичность отделена от отображения.** Все требования Спецификации §3 к ID выполнены:
   уникален, стабилен, неизменяем, не зависит от названия, не переиспользуется.
2. **Убирается самый хрупкий модуль проекта (риск R-07).** Раздел 17 v1.1 существует только потому,
   что в варианте A проводник показывает ULID. В варианте C проводник читаем, и подмена отображения
   не требуется ни в одной из 13 областей. Экономия — порядка 90 строк спецификации и модуля,
   зависящего от DOM и внутренних API.
3. **Obsidian помогает, а не мешает.** Штатное переименование файла автоматически обновляет ссылки
   по всему хранилищу — это проверенный механизм ядра, а не наш код.
4. **ULID вместо счётчика** снимает проблему конфликтов при синхронизации между устройствами
   (Obsidian Sync, git) и не требует центрального сервиса выдачи номеров.
5. **Скобки вместо длинного тире** — длинное тире с пробелами (`Название — ID`) визуально неотличимо
   от дефиса при быстром наборе и ломается при копировании; круглые скобки однозначно отделяют
   техническую часть и не конфликтуют с синтаксисом Markdown.

## 5. Последствия

### Положительные
- Проводник, поиск, быстрый переключатель, закладки, граф — всё читаемо **без единого адаптера**.
- Разрешение ссылок по стабильной подстроке надёжнее, чем по названию.
- Сортировка по ULID даёт хронологический порядок создания.

### Отрицательные / стоимость
- Имена файлов длиннее (название + 26 символов ULID + префикс). На файловых системах с ограничением
  255 байт длинное русское название может потребовать усечения `title` в имени файла.
  **Правило:** в имени файла используется не более 60 символов `title`, полный `title` — во frontmatter.
- Переименование объекта порождает переименование файла (но ссылки чинит Obsidian).
- Круглые скобки в именах файлов требуют экранирования в некоторых внешних инструментах
  (pandoc, shell-скрипты). Для shell — всегда кавычки.

### Что становится возможным позже
- При желании можно перейти на вариант A (только техническое имя) без смены `id` — идентичность не зависит
  от имени файла. Обратный переход также возможен. Это обратимое решение.

## 6. Влияние на метамодель

| Элемент | Было | Стало | Тип изменения |
|---|---|---|---|
| Формат `id` | `КОДТИПА-000001` / ULID (противоречие) | ULID, единственный формат | **BREAKING** (закрывает C-01) |
| Имя файла | `Название — ID.md` / `{PREFIX}-{ID}.md` (противоречие) | `{title} ({type_prefix}-{id}).md` | **BREAKING** (закрывает C-02) |
| Формат ссылки | два разных | `[[{title} ({prefix}-{id})\|{title}]]` | **BREAKING** (закрывает C-03) |
| `ObjectType.type_prefix` | не было поля (префикс подразумевался) | обязательное поле + реестр | additive (закрывает C-07) |
| Ограничение на `type_prefix` | не определено | ASCII `[A-Z][A-Z0-9]*`, сравнение по полному совпадению | clarification (закрывает C-06, C-08) |
| Длина `title` в имени файла | не определена | ≤ 60 символов | additive |
| Смена типа объекта | противоречие spec §17 ↔ v1.1 §1.5 | см. отдельное решение: `id` сохраняется, `type_prefix` и имя файла меняются контролируемой операцией | clarification (закрывает C-10, C-12) |

## 7. Миграция

- Требуется: **да, отложена**. Переименование файлов по новой схеме + нормализация всех ссылок.
- Что нужно сделать: однократная пакетная операция с предварительным просмотром и резервной копией
  (механизм описан в v1.1 §15.4).
- Когда: после MVP. До этого — новые объекты создаются по новой схеме, существующие читаются как есть.
- Затронутые файлы: все.
