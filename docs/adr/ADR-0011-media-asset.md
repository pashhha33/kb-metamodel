# ADR-0011: `MediaAsset`

## 1. Контекст и проблема

`MediaAsset` оставался последним типом M1 с неопределённым поведением. Черновики задавали семантические
роли и механизм контекстного разрешения (spec §12, v1.1 §10), но не определяли: связь обёртки с объектами,
кардинальность роли, механизм создания, источники изображения, именование бинарных файлов и правила
целостности. Диагноз зафиксировал пробелы G-5, G-7…G-11; видение пользователя добавило G-12…G-15
и требования T6…T14.

Пользователь принял: Q-41 = A, Q-42 = B, Q-43 = B, Q-44 = A, Q-37 = C и Q-40 = B (подтверждены ранее),
и подтвердил все четыре отклонения от черновика v1.1.

## 2. Ключевой структурный вывод

`MediaAsset` **уже является реификацией**: сырой файл — это «простая ссылка», а обёртка существует
потому, что у связи файла с объектом есть атрибуты (роли, источник, автор, лицензия, метод создания).
Это прямое следствие «правила повышения» X-03.

Следовательно, `Relation` поверх обёртки означал бы **двойную реификацию** и взрыв числа файлов:
паттерн N1 из Exocortex (31 828 троек → 37 339 файлов), отклонённый решением D-0016.

## 3. Решения

### 3.1. Связь с объектами — через свойства объекта (Q-37 = C)

Объект владеет связью: `Book.cover`, `Person.portrait`, `Organization.logo`, `Book.illustrations`.
Обёртка **не хранит** список объектов. Обратный список («какие объекты используют обёртку»)
**вычисляется** из `MetadataCache` (`embeds`, `frontmatterLinks`, `resolvedLinks`).

Обоснование: T8 формулирует запрос как «из поля `cover` объекта `book` подставить изображение обёртки» —
то есть как чтение свойства. Побочные следствия:

1. Алгоритм контекстного разрешения (v1.1 §10.1–10.2) **не реализуется как отдельный механизм** —
   его заменяют чтение свойства и фильтрация кандидатов. **Отклонение 1, подтверждено.**
2. Неоднозначность исчезает: у свойства одно значение или упорядоченный список (Q-40 = B).
3. Колонка в Bases появляется сама: `note.cover` — свойство frontmatter.

Новое необязательное поле **`Property.expected_media_roles`** (список значений enum `role`) — фильтр
кандидатов: свойство предлагает только обёртки, у которых хотя бы одна роль из списка входит в `roles`.

### 3.2. Роли — множественные (T10, закрывает G-6 и G-12)

Поле `role` переименовывается в **`roles`**, кардинальность `0..1` → **`0..n`**.

Это решает G-6 иначе, чем предполагалось в v0.1.0: роль остаётся свойством обёртки, но множественность
покрывает случай «одно изображение выполняет несколько ролей» без реификации пары.

| Роль | Значение enum |
|---|---|
| обложка | `cover` |
| баннер | `banner` |
| логотип | `logo` |
| портрет | `portrait` |
| аватар | `avatar` |
| превью | `preview` |
| фон | `background` |
| другая | `other` |

### 3.3. Метод создания — фасет и аспект (Q-41 = A, T9)

Вводится таксономия `Media` с фасетом `Creation method`:

```yaml
# Facet
---
type: facet
title: creation_method
label: Метод создания
key: creation_method
taxonomy: "[[Медиа (TAX-01J8Z6…)|Медиа]]"
hierarchy_mode: strict
assignment_cardinality: 0..n
root_requirement: multiple
---
```

Категории: `Фото`, `Коллаж`, `Рисунок`, `Генерация ИИ` (+ потомки: `Stable Diffusion`, `Midjourney` и др.).
Назначение хранится в `cat_creation_method` (ADR-0007).

Аспект активирует свойства метода генерации:

```yaml
---
type: aspect
title: ai_generated_media
label: Генерация ИИ
trigger_categories:
  - "[[Генерация ИИ (CAT-01J8Z6…)|Генерация ИИ]]"
properties:
  - "[[prompt (PROP-…)|Промпт]]"
  - "[[negative_prompt (PROP-…)|Негативный промпт]]"
  - "[[model (PROP-…)|Модель]]"
  - "[[seed (PROP-…)|Seed]]"
  - "[[sampler (PROP-…)|Сэмплер]]"
  - "[[steps (PROP-…)|Шаги]]"
  - "[[source_image (PROP-…)|Исходное изображение]]"
is_active: true
---
```

Активация включает потомков категории (ADR-0008 §3.2), поэтому подкатегория «Stable Diffusion»
также активирует аспект. `source_image` — ссылка на другую обёртку: производное изображение.

Обоснование выбора A: **ноль новых механизмов** — ADR-0007 и ADR-0008 применяются как спроектированы.
Это второй реальный случай применения `Aspect` после профессии, что подтверждает корректность механизма.

### 3.4. Галереи — привязка на стороне обёртки, порядок не хранится (Q-42 = B)

Пользователь отклонил рекомендацию A (`Gallery.items`) с обоснованием:

> «В галерее порядок изображений не важен, представление будет через Bases, а там много способов сортировки».

**Принято: `MediaAsset.galleries`** — список ссылок на `Gallery`, кардинальность `0..n`.

Обоснование принятия (сильнее первоначальной рекомендации A):

1. **Согласовано с ADR-0005 §3.1**: ссылки хранятся только «вверх», обратные вычисляются. Обёртка
   указывает на галерею; состав галереи вычисляется из обратных ссылок — штатным механизмом Obsidian
   (`MetadataCache.resolvedLinks`), без собственного индекса.
2. **Согласовано с ADR-0009 §3.1**: разделение — задача **представления**, а не хранения. Порядок
   изображений принадлежит `View` (сортировка Bases), а не данным.
3. **Пробел G-15 растворяется**: порядка, который надо выразить, больше нет. Механизм последовательностей
   ADR-0010 не применяется — и это правильно, поскольку он требует одного родителя.
4. Один факт в одном месте: принадлежность к галерее хранится один раз, на обёртке.

**Следствие для типа `Gallery`:** у него **нет** поля состава. Поля: системный контракт + `label`
+ `description` + необязательная `cover` (ссылка на `MediaAsset`). Вложенность галерей в MVP не вводится
(задел: поле `parent_gallery`, аддитивно).

Представление галереи — файл `.base` с фильтром «`galleries` содержит данную галерею» и сортировкой
по `View.definition`. Генерация таких файлов — задача фазы 5.

### 3.5. Тип `Gallery` включается в ядро MVP (закрывает G-13)

`Gallery` переводится из отложенных в конкретные типы MVP: **9-й конкретный тип**, первый в ветке
`Collection`, префикс `GALLERY` (был зарезервирован, становится активным). Изменяет ADR-0005 §3.3.

Итого предметных типов MVP: `Person`, `Character`, `Organization`, `Project`, `Task`, `Book`, `Chapter`,
`Article`, **`Gallery`**. Префиксов MVP: **21** (12 системных + 9 предметных).

### 3.6. Источники изображения при создании (Q-43 = B, T13)

| Источник | Статус в MVP | API | Ограничение |
|---|---|---|---|
| Непривязанные изображения хранилища | ✅ включён | `Vault.getFiles()` + фильтр по `TFile.extension` + вычитание индекса | — |
| Буфер обмена | ✅ включён | `navigator.clipboard.read()` + `Vault.createBinary`; запасной путь — `Workspace.on('editor-paste')` | **требует прототипа в фазе 5** |
| Путь к файлу на диске | ✅ включён | Node `fs` + `fileManager.getAvailablePathForAttachment` (`@since 1.5.7`) | **desktop-only**, изолированный модуль, пометка в README |
| URL в сети | ❌ **отложен** | `fetch` + `createBinary` | **Отклонение 3, подтверждено**: конфликт с рамкой «локально и офлайн» |

Задел: источник `url` добавляется позже как отдельный `Automation` с явной пометкой «требует сети».

### 3.7. Именование бинарных файлов (Q-44 = A, T12, закрывает G-14)

Конвенция ADR-0002 **распространяется на бинарные файлы**:

```
{title} ({type_prefix}-{id}).{ext}
```

Пример: `Обложка «Мастер и Маргарита» (MEDIA-01J8Z6M4K2Q7V9X3N5B0C1D2AC).jpg`

Три уточнения:

1. **Расширение сохраняется** из исходного файла (`jpg`, `jpeg`, `png`, `webp`, `avif`, `gif`).
2. **Усечение `title`** до 60 символов — как в ADR-0002; полный `title` во frontmatter обёртки.
3. **Коллизия имён** разрешается через `getAvailablePathForAttachment`, а не ручным счётчиком.

**Переименование выполняется только при создании и по явной команде**, не при каждой правке `title`.
Обоснование: вариант B (переименовывать при каждой правке) означал бы переименование файла и обновление
всех ссылок во всём хранилище на каждое изменение названия. Рассинхронизация имени файла и `title`
обнаруживается правилом `media.r9` (warn) и устраняется командой.

Переименование выполняется через `fileManager.renameFile` — Obsidian автоматически обновляет ссылки.

### 3.8. Технические метаданные не хранятся (G-11)

Ширина, высота, пропорции, размер файла **не хранятся** в обёртке. Читаются по требованию и кэшируются
в `.sb/cache/` с инвалидацией по событиям файлового API. Обоснование: принцип X-01 — один источник истины;
хранение создало бы устаревание при замене файла.

### 3.9. Миниатюры вместо списков (T14)

Выбор изображения в модалках отображает **миниатюры** через `Vault.getResourcePath(file)` —
документация API: *«Returns a URI for the browser engine to use, for example to embed an image»*.
Обязательны виртуализация списка и ленивая загрузка: отрисовка сотен `<img>` без виртуализации
деградует (открытый вопрос v1.1 §13 п.28).

### 3.10. Единая точка разрешения — `MediaResolver`

T6, T7, T8 и T14 выполняют одну операцию. Во избежание четырёх расходящихся реализаций вводится модуль:

```
MediaResolver
  byAsset(id | TFile)  → { asset, file, resourcePath }   // T7, T8, T14
  byImageFile(path)    → MediaAsset | null               // T6: привязано ли изображение
  reverseIndex         → Map<filePath, MediaAsset>       // инвалидация по событиям vault
```

Правила (из v1.1 §10.3, нормативные):
1. Разрешение **не изменяет** обёртку и её метаданные.
2. При отсутствии результата — **сообщить, не выбирать произвольное изображение**.
3. Разрешение по стабильному `id`, а не по совпадению строк названия (ADR-0002).
4. Индекс не является источником истины: источник — поле `file` в обёртках (X-01).

### 3.11. Граница применения обёртки (Q-38 = B, принято по умолчанию)

> Обёртка создаётся, когда изображению нужна **роль** или **собственные метаданные**
> (источник, автор, лицензия, метод создания). Иллюстрации внутри текста заметки остаются
> обычными вставками `![[file.png]]` и обёртки не требуют.

Создание — только по явному действию пользователя, никогда автоматически.

> **Примечание:** Q-38 не был подтверждён пользователем явно; значение принято как разумное
> по умолчанию и помечено как **предположение, которое можно изменить**.

### 3.12. Автозаполнение метаданных отложено (Q-39, отклонение 2 подтверждено)

Сценарий 2 из v1.1 §10.4 (автозаполнение свойств объекта данными обёртки) **не реализуется в MVP**.
Обоснование: это единственный сценарий темы, который **пишет данные в объект** на основании другого
объекта — максимальный риск с точки зрения принципа S6; требует allowlist, которого нет
(v1.1 §10.3: «только для явно определённых полей», поля не определены — открытый вопрос v1.1 §13 п.9).
Сценарий 1 (отображение) покрывает основную потребность.

Задел: `Property.auto_fill_from_media: boolean` — аддитивно.

### 3.13. Точки отрисовки и их этапы

| Требование | MVP | Этап 2 фазы 5 |
|---|---|---|
| T6 Кнопка у изображения | режим чтения (`registerMarkdownPostProcessor`, `0.9.7`) + контекстное меню редактора (`Workspace.on('editor-menu')`) | Live Preview через `registerEditorExtension` (CM6, `0.12.8`) — **отклонение 4, подтверждено** |
| T7 `![[обёртка]]` → изображение | `registerMarkdownPostProcessor` | — |
| T8 Изображение в Bases | **только собственное представление** через `registerBasesView` (`1.10.0`) | — |
| T8 Карточка объекта | собственный `ItemView` через `registerView` | — |
| T14 Миниатюры | `Vault.getResourcePath` + виртуализация | — |

**Ограничение, зафиксированное явно:** штатная таблица Bases отрисует чип ссылки, а не изображение, —
она не умеет разрешать свойство-ссылку в изображение другого объекта. Следствие: `minAppVersion: 1.10.0`
(D-0015) критично именно для T8, и прототип `registerBasesView` должен быть **первой** задачей фазы 5.

## 4. Поля `MediaAsset` (нормативно)

| Поле | Тип | Обяз. | Кард. | Описание |
|---|---|---|---|---|
| `file` | ссылка на файл хранилища | **да** | `1` | Единственная ссылка на физический файл |
| `media_kind` | enum | да | `1` | `image` \| `audio` \| `video` \| `document` |
| `roles` | enum (список) | нет | `0..n` | Роли, которые обёртка способна выполнять |
| `galleries` | список ссылок на `Gallery` | нет | `0..n` | Порядок не хранится (Q-42 = B) |
| `cat_creation_method` | список ссылок на `Category` | нет | по фасету | Метод создания; активирует аспекты |
| `source_url` | text | нет | `0..1` | Откуда взято (справочно) |
| `author` | reference → `Person` \| `Organization` | нет | `0..1` | Автор |
| `license` | text | нет | `0..1` | Лицензия |
| `description` | text | нет | `0..1` | Описание |

**Не хранятся:** `width`, `height`, `aspect_ratio`, `file_size` (§3.8).

Новое поле `Property`: `expected_media_roles` (список enum `role`, необязательное).

## 5. Правила целостности (`media.*`)

| ID | Уровень | Правило | Сообщение |
|---|---|---|---|
| `media.r1` | error | `file` присутствует и указывает на существующий файл хранилища | «Файл обёртки не найден: {факт}» |
| `media.r2` | error | `media_kind` и каждое значение `roles` входят в enum | «Недопустимое значение {поле}: {факт}» |
| `media.r3` | error | Каждая ссылка в `galleries` разрешима, ведёт на объект типа `gallery`, дубликаты отсутствуют | «Некорректная ссылка на галерею: {факт}» |
| `media.r4` | warn | Обёртка-сирота: на неё нет ссылок ни из свойств, ни из встраиваний | «Обёртка {title} не используется ни одним объектом» |
| `media.r5` | warn | Свойство с `expected_media_roles` ссылается на обёртку, у которой ни одна роль не совпадает | «Обёртка {title} не подходит для свойства {label}: ожидалась роль {список}» |
| `media.r6` | warn | Несколько обёрток указывают на один `file` | «Файл {path} используется несколькими обёртками: {список}» |
| `media.r7` | warn | Обёртка входит более чем в 5 галерей | «Обёртка {title} входит в {n} галерей — проверьте обоснованность» |
| `media.r8` | info | Файл вложения не имеет обёртки (норма по §3.11) | — |
| `media.r9` | warn | Имя бинарного файла не соответствует конвенции §3.7 | «Имя файла {факт} не соответствует каноническому; выполните команду переименования» |
| `naming.r11` | error | Имя бинарного файла соответствует `{title} ({PREFIX}-{id}).{ext}`, расширение сохранено | «Недопустимое имя медиафайла: {факт}» |

Каталог вырастает со 104 до **114 правил**.

## 6. Последствия

### Положительные
- Закрывает 9 пробелов (G-5, G-7…G-15) и все 9 требований T6…T14.
- `MediaAsset` — последний тип M1 с неопределённым поведением; после этого ADR ядро полное.
- Механизм `Aspect` получил второе применение — подтверждение корректности ADR-0008.
- Состав галереи вычисляется штатным механизмом Obsidian (`resolvedLinks`), без собственного индекса.
- Все механизмы проверены по публичному API; DOM-вмешательство не требуется нигде.

### Отрицательные / стоимость
- **BREAKING:** `role` → `roles` с изменением кардинальности.
- Ядро предметных типов выросло с 8 до 9; префиксов — с 20 до 21.
- T8 (изображение в Bases) жёстко привязан к `registerBasesView` и `minAppVersion: 1.10.0` —
  самая рискованная функция фазы 5, требует первого прототипа.
- Чтение буфера обмена требует прототипа; путь на диске — desktop-only.
- Переименование бинарных файлов по команде, а не автоматически, допускает временную рассинхронизацию
  имени файла и `title` (обнаруживается `media.r9`).
- Порядок в галерее не сохраняется в данных: если позже потребуется кураторская подборка с фиксированным
  порядком, его придётся выражать через `View` либо вводить `Gallery.items` как ломающее изменение.

### Что становится возможным позже
- Источник `url` как отдельный `Automation` с пометкой «требует сети».
- Автозаполнение метаданных через `Property.auto_fill_from_media`.
- Вложенные галереи через `parent_gallery`.
- Кнопка в Live Preview через CM6.
- Экспорт в RDF: `MediaAsset` → `dcterms:Image` / `foaf:Image`, `roles` → `dcterms:type`,
  `author` → `dcterms:creator`, `license` → `dcterms:license`, `source_image` → `prov:wasDerivedFrom`.

| Элемент | Было | Стало | Тип изменения |

## 8. Миграция

- Требуется: да, отложена. Переименование `role` → `roles` с изменением кардинальности
  (скаляр → список) добавляется к накопленному списку миграций.
- Накоплено **пять** миграций: (1) ключи RU→EN; (2) имена файлов и ссылки; (3) удаление дублей `title`
  из `aliases`; (4) распределение `categories` по `cat_<key>`; (5) `role` → `roles`.
- Правило безопасности прежнее: неразрешимое значение не мигрирует, попадает в отчёт, объект не
  перезаписывается (принцип S6).
