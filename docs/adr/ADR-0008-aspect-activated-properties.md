# ADR-0008: Aspect — активируемые свойства

## 1. Контекст и проблема

Требование **R-TRIGGER** (зарегистрировано в ADR-0006 §1, D-0032):

> Профессия должна выполнять роль триггера и привязывать к объекту дополнительные свойства,
> описывающие эту профессию.

Назначение категории «Писатель» должно делать применимыми свойства `pen_name`, `literary_period`;
назначение «Врач» — свойства `medical_specialization`, `license_number`.

Требование влечёт три отсутствующих элемента:

1. **Место хранения** набора активируемых свойств.
2. **Четвёртый источник** в алгоритме разрешения свойств (ADR-0003 §3.4): было
   `inherited → own → universal`, требуется `→ triggered`.
3. **Правило конфликта**: два активированных набора могут задать одно свойство с разными ограничениями.

Ключевое ограничение, выявленное при анализе: **профессий может быть несколько**. Булгаков — писатель
и врач, значит требуется **объединение** наборов свойств. Модель имеет одиночный `parent_type`
(ADR-0005, «только непосредственный родитель»), поэтому выразить это наследованием типов нельзя —
потребовалось бы множественное наследование со всеми его проблемами (ромбовидность, порядок разрешения).

## 2. Рассматриваемые варианты

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Список свойств прямо на `Category`: `Category.properties` | Новый тип не нужен; интуитивно; алгоритм расширяется одним источником | **Нет переиспользования:** «Писатель», «Поэт», `Драматург» требуют трёх копий одного набора. `Category` получает вторую ответственность (классификация + схема). Триггер — только категория |
| **B** | **Отдельный тип M1 `Aspect`** с `trigger_categories`, `properties`, `property_overrides` | Один аспект активируется многими категориями; `Category` остаётся только классификацией; триггер расширяем; структурно симметричен `ObjectType` | 12-й тип M1; ещё один уровень косвенности |
| C | Профессия как подтип: `Writer extends Person` | Ноль новых механизмов — наследование ADR-0003 уже это делает | **Не работает при нескольких профессиях** (нужно множественное наследование); теряется фасетная фильтрация «все писатели»; взрыв числа типов |

## 3. Решение

**Выбран вариант B.** Вводится 12-й тип M1 — `Aspect`.

### 3.1. Определение типа

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D3E1
type: aspect
title: literary_person
label: Литературная деятельность
layer: system
lifecycle: standard

trigger_categories:
  - "[[Писатель (CAT-01J8Z6…)|Писатель]]"
  - "[[Поэт (CAT-01J8Z6…)|Поэт]]"
  - "[[Драматург (CAT-01J8Z6…)|Драматург]]"

properties:
  - "[[pen_name (PROP-01J8Z6…)|Псевдоним]]"
  - "[[literary_period (PROP-01J8Z6…)|Литературный период]]"
  - "[[awards (PROP-01J8Z6…)|Премии]]"

property_overrides:
  - property: "[[pen_name (PROP-01J8Z6…)|Псевдоним]]"
    required: true

description: Свойства, применимые к человеку, занимающемуся литературной деятельностью.
is_active: true
---
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `label` | text | да | Подпись (ADR-0001) |
| `trigger_categories` | список ссылок на `Category` | да, `1..n` | Категории, назначающие которые объект получает свойства аспекта |
| `properties` | плоский упорядоченный список ссылок на `Property` | да, `1..n` | Активируемые свойства |
| `property_overrides` | вложенный список | нет | Ужесточения ограничений для свойств в контексте аспекта |
| `is_active` | boolean | да | Выключенный аспект не активируется; позволяет временно отключить набор без удаления |
| `description` | text | нет | — |

`Aspect` подчиняется системному контракту (8 полей) и имеет `layer: system`, `type_prefix: ASPECT`.

### 3.2. Активация включает потомков категории

> **Правило активации.** Аспект активируется, если среди назначенных объекту категорий есть
> либо сама категория из `trigger_categories`, **либо любой её потомок** (обход `Category.parent` вниз).

Обоснование: «Романист» — потомок «Прозаика», потомок «Писателя». Человек, отмеченный только
категорией «Романист», семантически является писателем и должен получить литературные свойства.
Точное совпадение без потомков заставило бы перечислять в `trigger_categories` всю ветку —
это дублирование иерархии, которое мы последовательно устраняем (ср. удаление `Taxonomy.facets`).

Флаг «учитывать только точное совпадение» в MVP **не вводится**. Добавить его позже — аддитивное
изменение `MINOR`.

### 3.3. Алгоритм разрешения свойств, редакция 2 (изменяет ADR-0003 §3.4)

Для объекта `O` типа `T`:

```
1. inherited  = свойства всех предков T (обход parent_type вверх)
2. own        = T.properties
3. universal  = все Property со scope: universal
4. triggered  = объединение A.properties для всех Aspect A, где
                  A.is_active == true
                  и ∃ c ∈ A.trigger_categories: c ∈ assigned(O) ∨ c ∈ ancestors(assigned(O))
                где assigned(O) = объединение всех списков cat_<facet_key> объекта O
5. effective  = union(inherited, own, universal, triggered)
6. для каждого P из effective:
     default  = ограничения из определения P
     override = последнее найденное property_overrides при обходе
                (a) от корня иерархии типов к T, затем
                (b) аспекты в порядке возрастания id (детерминированно)
     result   = override ?? default
7. проверка допустимости ужесточения (ADR-0003 §3.5)
```

**Пункт 6(b) вводит детерминированный порядок.** Без него результат зависел бы от порядка обхода
файлов, то есть валидация одного и того же объекта могла давать разные результаты на разных машинах.
Сортировка по `id` (ULID) стабильна и не требует настроек.

### 3.4. Правило конфликта

| Ситуация | Уровень | Действие |
|---|---|---|
| Два активированных аспекта задают одно свойство с **совместимыми** ограничениями (например, один `required: false`, другой `required: true`) | — | Применяется строжайшее по порядку из п. 6(b). Не ошибка |
| Два аспекта задают **несовместимые** ограничения (разная `cardinality`, не сводимая к сужению; разные `allowed_values`) | `error` | Ошибка **при загрузке метамодели**, не при правке объекта. Плагин сообщает о паре аспектов и свойстве; последняя корректная схема продолжает использоваться (принцип v1.1 §15.5) |
| Аспект активирует свойство, уже заданное типом объекта с другими ограничениями | `warn` | Приоритет у типа объекта (п. 6: `own` разрешается до `triggered`); сообщение подсказывает убрать дубль |

**Отклонённая альтернатива:** «побеждает строжайшее» для всех случаев. Отклонено, потому что
маскирует ошибку проектирования метамодели: пользователь не узнает, что два аспекта противоречат
друг другу, и будет видеть необъяснимые требования обязательности.

### 3.5. Что НЕ делает аспект

1. **Не создаёт отдельный объект-«профиль».** Значения активируемых свойств хранятся в плоском
   frontmatter самого объекта. Это подтверждённая интерпретация R-TRIGGER.
2. **Не удаляет значения автоматически.** Если категория-триггер снята, а значение свойства осталось —
   это `warn` (`aspect.r1`), а не удаление. Принцип S6: система не переписывает данные молча.
3. **Не наследуется по иерархии типов.** Аспекты привязаны к категориям объекта, а не к его типу.
   Объект типа `Book` не получает аспекты, активированные категориями его автора.
4. **Не заменяет `property_overrides` типа.** Оба механизма сосуществуют: тип задаёт базовый состав,
   аспекты добавляют контекстно-зависимый.

### 3.6. Расширение триггера (задел, в MVP не реализуется)

В MVP `trigger_categories` — единственный вид триггера. Конструкция допускает позже добавить
без ломающих изменений:

| Будущий триггер | Поле | Пример |
|---|---|---|
| По типу отношения | `trigger_relation_types` | Наличие связи `member_of` активирует «служебные» свойства |
| По значению свойства | `trigger_conditions` | `status == archived` активирует «архивные» свойства |
| По типу объекта | `trigger_types` | Все объекты типа `Character` получают свойства персонажа |

Все три — необязательные поля, семантика «ИЛИ» между всеми триггерами. Аддитивные изменения `MINOR`.

## 4. Обоснование

1. **Переиспользование.** Один аспект «Литературная деятельность» активируется категориями
   «Писатель», «Поэт», «Драматург». При варианте A потребовались бы три копии списка свойств,
   расходящиеся со временем.
2. **Единственная ответственность `Category`.** Категория — самый массовый и чаще всего редактируемый
   пользователем объект M1. Вешать на него схему означало бы, что правка классификации может
   незаметно сломать валидацию.
3. **Объединение вместо множественного наследования.** Несколько профессий дают несколько аспектов;
   их свойства объединяются. Ромбовидность невозможна, потому что аспекты не наследуются друг от друга.
4. **Симметрия с `ObjectType`.** У аспекта те же `properties` и `property_overrides`, что у типа, —
   один механизм ограничений, одно правило ужесточения, один код разрешения.
5. **Расширяемость триггера** (§3.6) без ломающих изменений.

## 5. Последствия

### Положительные
- R-TRIGGER закрыт: профессия действительно активирует свойства.
- Множественные профессии работают без множественного наследования.
- Один и тот же механизм позже покроет роли, статусы и типы отношений.

### Отрицательные / стоимость
- **Ядро M1: 11 → 12 типов.** Все перечни, диаграммы и будущая JSON Schema должны учитывать `Aspect`.
- Алгоритм разрешения свойств усложнился с 6 до 7 шагов и требует детерминированного порядка.
  **Митигция:** модуль разрешения покрыт юнит-тестами на все 7 шагов (обязательное условие фазы 3).
- Проверка применимости свойства требует знания назначенных категорий и их предков — то есть
  обхода иерархии категорий. **Митигция:** кэш предков в `.sb/cache/` с инвалидацией по событиям
  файлового API.
- Пользователю труднее понять, почему у объекта появилось поле. **Митигция:** UI плагина показывает
  для каждого поля источник («тип», «универсальное», «аспект: Литературная деятельность»).

### Что становится возможным позже
- Аспекты по типу отношения и по значению свойства (§3.6).
- Пакетная поставка аспектов вместе с фасетами (идея E4 из Exocortex).
- Экспорт в RDF: `Aspect` → `owl:Class` с `owl:equivalentClass` от пересечения триггерных концептов,
  либо как `sh:NodeShape` с `sh:targetClass` — в зависимости от выбранного позже профиля.

## 7. Миграция

- Требуется: нет. Определений M1 в хранилище пока нет.
- Зафиксировано на будущее: если позже будет добавлен флаг «только точное совпадение категории»,
  существующие аспекты получат значение по умолчанию `true` (учитывать потомков), то есть поведение
  не изменится. Миграция не потребуется.
