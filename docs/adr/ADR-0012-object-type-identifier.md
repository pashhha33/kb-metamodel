# ADR-0012: Идентификатор типа хранится в определении (`ObjectType.type_id`)

## 1. Контекст и проблема

ADR-0005 §3.6 (D-0020) установил: экземпляр M0 хранит `type` строкой snake_case (например,
`type: book`), которая проверяется **по реестру типов (индексу плагина)**, а не разрешением ссылки.
Индекс нужен не только для этой проверки: `contract.r5` (экземпляры абстрактных типов не создаются),
`link.r2` (тип цели соответствует `target_types`), `relation.r2/r3` (типы концов связи с учётом
наследования), `meta.r14/r15` (принадлежность свойств типу), эффективный набор свойств — всё это
требует соответствия «значение `type` → определение `ObjectType`».

Но **ни одно поле определения `ObjectType` не хранит это значение** (находка F-3.27, обнаружена
при написании `entities/object_type.md`, фаза 3c). Схема 0.14.0 знает только формат
(`enums.json#/$defs/type_id`: «проверяется по индексу типов»), а сам индекс построить из данных
нечем. Следствия:

1. Песочница примеров хардкодит соответствие префиксов (`CHAR → character`, `ORG → organization`) —
   оно **невыводимо** из префикса и существует только в коде.
2. Генератор примеров берёт `type_id` из внешнего реестра (`vault-data.cjs`), которого нет
   в нормативной модели.
3. Типы, добавляемые как данные M1 без ADR и релиза (ADR-0005 §3.3, D-0021 — «остальные 27 типов»),
   фактически объявить нечем: у нового определения нет носителя идентификатора.

## 2. Рассматриваемые варианты

| # | Вариант | Плюсы | Минусы | Последствия |
|---|---|---|---|---|
| A | Обязательное поле `ObjectType.type_id` (EN snake_case, уникален, неизменяем) по образцу `Facet.key` (ADR-0007) | Индекс строится из самих данных; произвольные типы как данные (D-0021) реально возможны; хардкод устранён; симметрия с `Facet.key`; «слой key» ADR-0001 становится явным для типов | Новое обязательное поле (формально breaking для формы); +2 правила в каталог; перевыпуск схемы | ADR + схема 0.15.0 + заполнение в каноне |
| B | Конвенция «`type_id` = `type_prefix` в нижнем регистре» + таблица исключений в реестре префиксов | Без изменения схемы и каталога | Конвенция уже нарушена двумя типами ядра (`CHAR → character`, `ORG → organization`); префикс и идентификатор — разные сущности (у префикса свои правила: омоглифы, длина 3–12); новые типы-данные вынуждены подгонять префикс под идентификатор | Таблица исключений растёт; семантика префикса размывается |
| C | Отложить в фазу 4/5: индекс строит плагин «как умеет» | Ноль работы сейчас | Дыра остаётся: описание `ObjectType` неполно, `MetamodelLoader`/`ObjectIndex` без нормативного источника, цена решения растёт с каждой новой сущностью | Технический долг переносится в реализацию |

## 3. Решение

Мы выбираем **вариант A**: определение `ObjectType` получает обязательное поле `type_id` —
идентификатор типа, который его экземпляры носят в поле `type`. Формат — `^[a-z][a-z0-9_]*$`
(EN snake_case, ≤ 64, по `enums.json#/$defs/type_id`); значение **глобально уникально** среди
определений `ObjectType` и **не совпадает** с идентификаторами системных типов M1; после создания
**не изменяется** (изменение = миграция типа, отложена до после-MVP). Индекс типов строится
исключительно из данных хранилища; соответствие префиксов кодом не хардкодится.

## 4. Обоснование

- **Симметрия с `Facet.key`** (ADR-0007, D-0029): ключ обязателен, уникален, неизменяем,
  участвует в производных именах (`cat_<key>`); `type_id` — тот же «слой key» (ADR-0001) для типов.
- **«Всё как данные»** (X-04, D-0016): индекс типов — производное от содержимого хранилища,
  а не от кода плагина или песочницы.
- **D-0021 становится выполнимым**: произвольный предметный тип добавляется одной заметкой
  с `type_id`, без правки кода.
- **Префикс и идентификатор — независимые сущности**: префикс живёт в имени файла и ссылках
  (правила реестра D-0018), идентификатор — в поле `type` экземпляров; вариант B смешал бы их.

## 5. Последствия

### Положительные
- Индекс типов, `contract.r5`, `link.r2`, `relation.r2/r3`, `meta.r14/r15`, эффективный набор
  свойств получают нормативный источник в данных.
- Хардкод `PREFIX_TO_TYPE`/`PREFIX_TO_TYPE_REV` удаляется из песочницы; загрузчик плагина
  (фаза 5) строит индекс из поля.
- Описание `entities/object_type.md` закрывает §4 без оговорки «не хранится».

### Отрицательные / стоимость
- Новое обязательное поле: формально ломающее изменение формы; данных в хранилище пользователя
  нет, поэтому выпуск **MINOR** (0.15.0).
- Каталог правил 115 → 117 (`naming.r12` формат — схема, `naming.r13` уникальность и несовпадение
  с M1 — валидатор).
- Каноническое хранилище и контрольные примеры пересобираются (производные — скриптами).

### Что становится возможным позже
- Экспорт пакета метамодели (D-0016, E4): типы пакета идентифицируются `type_id`.
- Миграция типа экземпляра (с сохранением `id`, ADR-0002) — после MVP.

## 6. Влияние на метамодель

| Элемент | Было | Стало | Тип изменения |
|---|---|---|---|
| `ObjectType.type_id` | отсутствовал (индекс нечем построить, F-3.27) | обязательное поле, EN snake_case, уникально, неизменяемо | additive для схемы / breaking для формы (данных нет → MINOR) |
| `naming.r12` | — | `type_id` соответствует формату `type_id` | новое правило (error, схема) |
| `naming.r13` | — | `type_id` уникален среди `ObjectType` и не совпадает с M1-типами | новое правило (error, валидатор) |
| Условие `meta.r16` | каталог 0.15.0 (RULES), песочница | условное ограничение схемы (D-0072) | additive |
| Description `sequential_parent` | «`cardinality: 1`» | «`cardinality ∈ {1, 0..1}`» (F-3.26, по `sequence.r2`) | clarification |

## 7. Миграция

- Требуется: нет (данных в хранилище пользователя нет).
- Что нужно сделать: каноническое хранилище примеров и контрольные примеры пересобраны скриптами
  (`type_id` заполнен из реестров `tools/examples/data-types.cjs` и генератора фикстур).
- Когда: —. Накопленный список миграций (пять позиций) не меняется; изменение `type_id` существующего
  типа стало бы шестой миграцией — запрещено до отдельного решения.
