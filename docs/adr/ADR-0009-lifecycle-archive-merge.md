# ADR-0009: Жизненный цикл, архивирование, слияние и миграция

## 1. Контекст и проблема

Спецификация объявляет три механизма, не определяя их физически (противоречие C-32):

- §15 — жизненный цикл данных: `Захват → Черновик → Нормализация → Активный → Архивный → Удаление`;
  физическое удаление — отдельная административная операция.
- §17 — миграция при изменении типа: «старый объект архивируется, связь между объектами фиксируется».
  Тип связи не назван.
- §18 — архивирование предпочтительнее удаления; при объединении: выбрать основной объект,
  перевести ссылки, дубликат архивировать, историю сохранить. Способ фиксации не определён.

Поле `status` уже введено в системный контракт (закрыло C-31), но оставались не определены:
физическое выражение архивирования и связи, фиксирующие замену и слияние.

Дополнительно ADR-0002 изменил правило смены типа: `id` сохраняется, меняются `type_prefix` и имя файла.
Это отменяет часть Спецификации §17 («создаётся новый объект, получает новый ID»), поэтому связь замены
нужна не для смены типа, а для случаев, когда объект действительно заменяется другим объектом.

## 2. Рассматриваемые варианты

### 2.1. Физическое выражение архивирования (Q-30)

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **A** | Только поле `status: archived` | Один источник факта; ссылки остаются валидными (файл на месте); Bases и граф фильтруются по `status`; поле уже в контракте | В проводнике архивные объекты смешаны с активными |
| B | `status` + перемещение файла в `Archive/` | Визуальное разделение; папку можно исключить из поиска и графа | **Два источника одного факта**: поле и расположение файла расходятся |
| C | `status` + связь `archived_in` | Явная семантика | Связь не добавляет информации к полю |

### 2.2. Связи слияния и миграции (Q-31)

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Один тип `supersedes` | Минимум типов | Смешивает замену (1:1) и слияние (N:1): разные кардинальность и последствия |
| **B** | Два типа: `supersedes` (1:1) и `merged_into` (N:1) | Семантика и кардинальность разделены; покрывает spec §17 и §18 | Два типа отношений |
| C | Три типа: + `duplicate_of` | Явно помечает дубль до решения о слиянии | `duplicate_of` — диагноз, а не состояние данных; после слияния заменяется на `merged_into`. Третье понятие с неясным жизненным циклом |

## 3. Решение

### 3.1. Архивирование — только поле `status` (вариант A)

1. Архивирование выражается значением `status: archived`. Файл **не перемещается**, имя файла не меняется.
2. Разделение «активное / архив» — задача **представления**, а не хранения: `View` с `mechanism: bases`
   и фильтром `status != archived`.
3. `status: deleted` — отметка, а не удаление файла. Физическое удаление остаётся отдельной
   административной операцией с резервной копией (Спецификация §15, v1.1 §15.6).
4. Архивный объект остаётся полноправной целью ссылок: ссылки не становятся битыми.

Обоснование: принцип «один факт — одно место», применённый ранее трижды (удаление `Taxonomy.facets`,
замена плоского `categories` на `cat_<key>`, отклонение варианта C в ADR-0007). Вариант B создал бы
второй источник состояния и класс ошибок «файл в `Archive/`, но `status: active`».

### 3.2. Два типа отношений (вариант B)

| `RelationType` | `title` | Направление | Кардинальность | `uniqueness_rule` | Семантика |
|---|---|---|---|---|---|
| Замена | `supersedes` | `subject` → `object`: **новый** объект заменяет **старый** | `0..1` у субъекта | `unique_subject` | Объект заменён другим объектом (версия, переработка, разделение сущности) |
| Слияние | `merged_into` | `subject` → `object`: **дубликат** влит в **основной** | `0..1` у субъекта | `unique_subject` | Несколько объектов схлопнуты в один основной (Спецификация §18) |

Оба — объекты `Relation`, потому что несут атрибуты: `description` (что именно перенесено),
`valid_from` (когда выполнено), `source_ref` (основание). По «правилу повышения» X-03 это обязательно.

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D4F1
type: relation
title: Слияние дубликата «Мастер и Маргарита (рукопись)»
subject: "[[Мастер и Маргарита (рукопись) (BOOK-01J8Z6…)|…]]"
relation_type: "[[Слито в (RTYPE-01J8Z6…)|Слито в]]"
object: "[[Мастер и Маргарита (BOOK-01J8Z6…)|Мастер и Маргарита]]"
valid_from: 2026-10-21
description: Перенесены свойства publication_date и categories; ссылки переведены.
---
```

### 3.3. Процедура слияния (нормативная, из Спецификации §18)

1. Пользователь выбирает основной объект.
2. Плагин показывает **предпросмотр**: какие свойства будут перенесены, какие ссылки затронуты,
   какие конфликты возникнут (v1.1 §15.4 п.5).
3. После подтверждения создаётся резервная копия.
4. Ссылки переводятся на основной объект.
5. Создаётся объект `Relation` с `relation_type: merged_into`.
6. Дубликату присваивается `status: archived`. Файл не удаляется и не перемещается.
7. История сохраняется: объект-дубликат остаётся доступным, связь фиксирует факт и основание.

Шаги 4–6 выполняются как одна операция; при сбое любого шага изменения откатываются из резервной копии.

### 3.4. Правила валидации

| ID | Уровень | Правило | Сообщение |
|---|---|---|---|
| `lifecycle.r1` | error | Цель `merged_into` и `supersedes` не имеет `status: archived` — цепочки запрещены, всегда один переход | «Цель связи {title} архивная; цепочки замен запрещены. Укажите конечный объект» |
| `lifecycle.r2` | warn | На архивный объект ссылаются активные объекты | «На архивный объект {title} ссылаются активные: {список}. Вероятно, ссылки надо перевести» |
| `lifecycle.r3` | error | У объекта не более одного исходящего `merged_into` и не более одного `supersedes` | «Объект {title} имеет несколько связей замены» |
| `lifecycle.r4` | warn | Объект со `status: deleted`, но файл существует и ссылки на него не переведены | «Объект отмечен как удалённый, но ссылки на него остались» |
| `lifecycle.r5` | info | Переход `status` нарушает порядок жизненного цикла (§15) | «Необычный переход статуса: {откуда} → {куда}» |

Правило `lifecycle.r5` — `info`, а не `error`: Спецификация §15 задаёт порядок как основной путь,
но обратные переходы легитимны (архивный объект может быть возвращён в активные).

## 4. Обоснование

1. **Архивирование полем** сохраняет ссылки валидными и не создаёт второго источника состояния.
2. **Разделение `supersedes` и `merged_into`** соответствует разной кардинальности: слияние — N:1,
   замена — 1:1. Объединение их в один тип потребовало бы проверять контекст, чтобы понять направление.
3. **Запрет цепочек** (`lifecycle.r1`) устраняет транзитивное разрешение: чтобы найти актуальный объект,
   всегда достаточно одного перехода. Без этого правила потребовался бы обход цепочки и защита от циклов.
4. **Процедура слияния нормативна**, а не описательна: предпросмотр и резервная копия обязательны,
   откат определён. Это прямое развитие принципа S6.
5. **`duplicate_of` не введён**: это диагноз, который разрешается либо слиянием (`merged_into`),
   либо снятием подозрения. Хранить его как состояние данных — значит плодить сущность с неясным
   жизненным циклом. Добавить позже можно аддитивно.

## 5. Последствия

### Положительные
- Закрывает C-32 — последнюю содержательную позицию диагноза.
- Архивирование, слияние и миграция стали реализуемыми: есть поле, есть связи, есть правила, есть процедура.
- Запрет цепочек делает разрешение замены O(1).

### Отрицательные / стоимость
- Проводник не показывает архив визуально. **Митигция:** `View` с фильтром по `status`;
  при необходимости плагин может добавить CSS-класс на элемент проводника — но это DOM-интеграция,
  запрещённая правилом P-API-1 (D-0014), поэтому в MVP не делается.
- Слияние — самая опасная операция в плагине: требует предпросмотра, резервной копии и атомарности.
  **Митигция:** процедура §3.3 нормативна; операция не входит в минимум стабильного ядра и переносится
  на поздний этап фазы 5.

### Что становится возможным позже
- `duplicate_of` как отдельный тип отношения (аддитивно).
- Журнал изменений объекта (v1.1 §15.6) — `valid_from` на связях замены уже даёт основу для истории.
- Экспорт в RDF: `supersedes` → `dcterms:isReplacedBy`, `merged_into` → `dcterms:isReplacedBy`
  с квалификатором слияния; `status: archived` → `vs:status` или `dcterms:valid`.

## 6. Влияние на метамодель

| Элемент | Было | Стало | Тип изменения |
|---|---|---|---|
| Архивирование | не определено физически | `status: archived`, файл не перемещается | clarification |
| `RelationType` `supersedes` | отсутствовал | введён, `unique_subject`, `0..1` | additive |
| `RelationType` `merged_into` | отсутствовал | введён, `unique_subject`, `0..1` | additive |
| Правила `lifecycle.r1…r5` | отсутствовали | введены | additive |
| Процедура слияния | описательная (spec §18) | нормативная, 7 шагов, с откатом | clarification |
| Спецификация §17 «новый объект получает новый ID» | действовало | **отменено** для смены типа (ADR-0002): `id` сохраняется. Связь замены применяется, когда объект действительно заменяется другим объектом | **BREAKING** для spec §17 |

## 7. Миграция

- Требуется: нет (данных в хранилище нет).
- Зафиксировано: если позже будет введена папка `Archive/`, это будет **представление**, а не изменение
  хранения; автоматическое перемещение файлов не планируется.
