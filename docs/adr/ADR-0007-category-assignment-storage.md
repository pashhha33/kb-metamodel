# ADR-0007: Хранение назначений категорий

## 1. Контекст и проблема

ADR-0005 установил: объект M0 хранит плоский список `categories`, а принадлежность категории к оси
определяется обходом `Category.facet`. Сопоставление с канонической моделью классификации
(`02_concept_alignment.md` §4.4) показало два следствия:

1. **Проверка кардинальности фасета требует разрешения каждой ссылки.** Чтобы понять, не нарушено ли
   `assignment_cardinality: 0..1` фасета «Тональность», нужно для каждой категории в списке прочитать
   её фасет. Стоимость линейна по числу назначений на каждой проверке.
2. **Bases не может построить колонку на ось.** Bases строит колонки по именам свойств frontmatter
   (`BasesPropertyType = 'note'`). При плоском списке получается одна колонка со смешанными категориями
   всех осей. Таблица «Книги с колонкой Жанр» невозможна без формулы.

Каноническая модель описывает объект как «основная категория таксономии **+ набор значений фасетов**» —
то есть значение привязано к своей оси явно.

## 2. Рассматриваемые варианты

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Плоский список `categories` | Одно поле; нет зависимости от имён фасетов; тривиальный парсинг | Кардинальность проверяется обходом ссылок; в Bases одна колонка со свалкой |
| **B** | **Ключи по фасетам: `cat_<facet_key>`** | Колонка Bases на каждую ось; кардинальность = длина списка; нативная панель Properties редактирует каждое поле отдельно | Нужно поле `Facet.key`; переименование фасета требует миграции имён полей |
| C | Плоский `categories` как канон + плагин дописывает производные `cat_*` | Совмещает преимущества | **Нарушает принцип «один факт — одно место»**, применённый при удалении `Taxonomy.facets`. Отклонён |

## 3. Решение

**Выбран вариант B.**

### 3.1. Новое поле `Facet.key`

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D3A2
type: facet
title: genre
label: Жанр
key: genre                       # ← новое обязательное поле
taxonomy: "[[Классификация произведений (TAX-01J8Z6…)|…]]"
hierarchy_mode: strict
assignment_cardinality: 0..n
root_requirement: multiple
---
```

Ограничения на `key`:

| Правило | Значение |
|---|---|
| Формат | `^[a-z][a-z0-9_]{1,30}$` |
| Уникальность | глобально среди всех `Facet` (не в пределах таксономии) — иначе имена полей collide |
| Неизменяемость | после первого использования в объектах изменение требует миграции |
| Запрет | не должно начинаться с `cat_` (во избежание `cat_cat_genre`) |

### 3.2. Поле назначения на объекте

Имя поля = `cat_` + `key` фасета. Значение — список ссылок на `Category` **этого фасета**.

```yaml
# Файл: Мастер и Маргарита (BOOK-01J8Z6M4K2Q7V9X3N5B0C1D2AC).md
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D2AC
type: book
title: Мастер и Маргарита
status: active

cat_genre:
  - "[[Научная фантастика (CAT-01J8Z6…)|Научная фантастика]]"
cat_tone:
  - "[[Мрачная (CAT-01J8Z6…)|Мрачная]]"
cat_profession: []                # пусто — допустимо при assignment_cardinality 0..n
---
```

### 3.3. Системный контракт: изменение

Поле `categories` **удалено** из системного контракта. Назначения категорий больше не являются
системным полем фиксированного имени — они порождаются определениями фасетов.

Системный контракт после изменения (8 полей):
`id` · `type` · `title` · `aliases` · `created_at` · `updated_at` · `status` · `tags`

Поля `cat_*` относятся к **расширяемому системному слою** (понятие из черновика v1.1 §14.1,
решение «B: фиксированное ядро плюс расширяемый системный слой»): их состав определяется метамоделью,
а инварианты обеспечивает ядро плагина.

### 3.4. Зарезервированное пространство имён

Префикс `cat_` зарезервирован. Ни один `Property.key` не может начинаться с `cat_`.
Проверка выполняется при сохранении определения свойства — `error`.

### 3.5. Валидация

| ID | Уровень | Правило |
|---|---|---|
| `classif.r10` | error | Поле `cat_<key>` существует только для фасета с таким `key` |
| `classif.r11` | error | Каждая ссылка в `cat_<key>` ведёт на `Category`, у которой `facet.key == <key>` |
| `classif.r3` | error | Длина списка `cat_<key>` соответствует `assignment_cardinality` фасета — **проверка стала тривиальной** |
| `classif.r12` | warn | Обнаружено поле `cat_*`, для которого нет фасета — вероятно, фасет удалён или переименован |

Правило `classif.r2` (тип объекта входит в `applicable_types` таксономии) проверяется по таксономии
фасета, как и прежде.

### 3.6. Интеграция с Bases

Плагин при генерации файла `.base` создаёт колонку на каждый фасет, применимый к целевому типу:

| Колонка | Источник | `displayName` |
|---|---|---|
| `note.cat_genre` | поле frontmatter | `Facet.label` = «Жанр» |
| `note.cat_tone` | поле frontmatter | `Facet.label` = «Тональность» |

`displayName` берётся из `label` (ADR-0001) и записывается в `BasesConfigFile.properties[*].displayName` —
механизм подтверждён публичным API (`@since 1.10.0`).

## 4. Обоснование

1. **Делает представления реальными.** Требование «представления: граф, таблицы, карточки, канбан, запросы»
   без этого решения невыполнимо средствами Bases: колонка на ось невозможна.
2. **Удешевляет валидацию.** Кардинальность фасета проверяется длиной списка, без разрешения ссылок.
3. **Согласуется с канонической моделью**, где значение привязано к своей оси явно.
4. **Нативная панель Properties редактирует каждое поле отдельно** — вложенный YAML не требуется
   (ограничение Obsidian, зафиксированное в ADR-0003 как риск R-11).
5. **Принцип одного источника соблюдён:** вариант C отклонён именно из-за его нарушения.

## 5. Последствия

### Положительные
- Таблицы Bases с колонкой на каждую ось классификации.
- Проверка кардинальности — O(1) на фасет.
- Видно в исходном коде заметки, к какой оси относится каждая категория.

### Отрицательные / стоимость
- **BREAKING:** поле `categories` удалено из системного контракта.
- Новый обязательный атрибут `Facet.key` с требованием глобальной уникальности.
- Переименование `key` фасета требует миграции имён полей во всех объектах.
  **Митигция:** плагин запрещает изменение `key` после первого использования без явной миграции
  с предпросмотром (механизм из v1.1 §15.4).
- Состав полей объекта зависит от метамодели: добавление фасета не добавляет поле автоматически.
  Поле появляется при первом назначении категории. Отсутствие поля эквивалентно пустому списку.

### Что становится возможным позже
- Группировка и канбан по любой оси без формул.
- Фильтрация кандидатов по категориям (`target_categories`, вопрос Q-29).

## 6. Влияние на метамодель

| Элемент | Было | Стало | Тип изменения |
|---|---|---|---|
| Системный контракт | 9 полей, включая `categories` | 8 полей, `categories` удалено | **BREAKING** |
| `Facet.key` | отсутствовало | обязательное, `^[a-z][a-z0-9_]{1,30}$`, глобально уникальное | **BREAKING** для определений фасетов |
| Поля назначений | `categories: [...]` | `cat_<facet_key>: [...]` | **BREAKING** |
| Пространство имён `cat_` | не зарезервировано | зарезервировано, запрещено для `Property.key` | additive |
| Проверки целостности | 9 правил | 12 правил (добавлены r10, r11, r12; r3 упрощена) | additive |

## 7. Миграция

- Требуется: **да, отложена**.
- Что нужно сделать: для каждого объекта прочитать `categories`, разрешить фасет каждой категории,
  распределить ссылки по полям `cat_<facet_key>`, удалить `categories`.
- Когда: вместе с общей миграцией имён (ADR-0001) и имён файлов (ADR-0002), после MVP.
- Затронутые файлы: все объекты M0 с назначениями категорий.
- Риск: категория с нерезолвящимся фасетом → не мигрирует, попадает в отчёт об ошибках,
  объект не перезаписывается (принцип S6: не молча переписывать данные).
