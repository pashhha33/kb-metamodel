# ADR-0010: Последовательности, scoped uniqueness, шаблон заголовка, форма создания

## 1. Контекст и проблема

Первый живой сценарий пользователя («Глава») выявил четыре пробела в модели (G-1…G-4,
см. `docs/metamodel/03_chapter_scenario.md` §2):

| ID | Пробел | Требование пользователя |
|---|---|---|
| G-1 | Нет способа объявить «тип является упорядоченной последовательностью внутри родителя» | T3 (кнопки «предыдущая/следующая/к книге»), T4 (автосоздание соседа) |
| G-2 | Нет уникальности в области действия: пара (`part_of`, `order`) должна быть уникальна | корректная нумерация глав |
| G-3 | Нет шаблона заголовка по умолчанию | T5 (имя можно пропустить → «Глава N») |
| G-4 | Нет определения формы создания | T2 (модалка: родитель, номер, имя) |

Пользователь принял решения Q-33 = B, Q-34 = C, Q-35 = A + C, Q-36 = A.

## 2. Решения по вопросам

### 2.1. Q-33 = B: ключ сортировки отделён от отображаемого обозначения

| Поле | Тип | Семантика |
|---|---|---|
| `order` | `number`, `cardinality: 1` | **Ключ сортировки.** Только число, используется для поиска соседей |
| `chapter_label` | `text`, `cardinality: 0..1` | **Отображаемое обозначение:** «Пролог», «1.2», «Эпилог» |

Обоснование: вариант A (одно текстовое поле) ломает сортировку — лексикографически `"10" < "2"`,
поэтому кнопки «соседняя глава» давали бы неверный результат. Разделение ключа и подписи повторяет
паттерн `key` / `label` из ADR-0001.

**Правило вычисления `title` при создании:**

```
title = chapter_label, если задан и непуст
      = title_template с подстановкой, если chapter_label пуст
      = error (contract.r6), если и шаблон не задан
```

Для «Пролога»: `order: 0`, `chapter_label: Пролог`, `title: Пролог`.
Для обычной главы без имени: `order: 70`, `chapter_label: ""`, `title: Глава 7`.

### 2.2. Q-34 = C: шаг нумерации настраивается, по умолчанию 10

Вводится необязательное поле `ObjectType.sequence_step: number` (по умолчанию `10`)
и `ObjectType.sequence_direction: enum` (`ascending` | `descending`, по умолчанию `ascending`).

| Операция | Вычисление нового `order` |
|---|---|
| Создать следующую | `max(order среди соседей) + sequence_step` |
| Создать предыдущую | `min(order среди соседей) − sequence_step` |
| Вставить между двумя | `round((order_a + order_b) / 2)`; если результат совпадает с одним из соседей — `warn` и предложение перенумеровать |
| Первая глава в книге | `sequence_step` (для `ascending`) |

Обоснование: плотная нумерация (1, 2, 3) потребовала бы перенумерации всех следующих глав при вставке —
а это правка `order` и, возможно, `title` у десятков файлов. Разреженная нумерация делает вставку
локальной операцией. Внутренние значения («некрасивые» 70, 80) пользователь не видит:
отображается `chapter_label` либо `title`, вычисленный из шаблона.

### 2.3. Q-35 = A + C: навигация в режиме чтения и в панели плагина

| Этап | Механизм | API | Версия |
|---|---|---|---|
| **MVP, вариант A** | Панель навигации в **режиме чтения** | `registerMarkdownPostProcessor` | `@since 0.9.7` |
| **MVP, вариант C** | Отдельная панель плагина — навигация доступна в любом режиме | `registerView` | — |
| **Этап 2 фазы 5** | Виджет в **Live Preview** (кнопки в теле при редактировании) | `registerEditorExtension` (CodeMirror 6) | `@since 0.12.8` |
| **Этап 2 фазы 5** | Явное размещение блоком ```` ```sb-nav ```` | `registerMarkdownCodeBlockProcessor` | `@since 0.9.7` |

Обоснование: A и C используют самые устойчивые публичные точки и не зависят от содержимого заметки.
Live Preview (вариант D) — единственный вариант с реальной вероятностью поломки при обновлении Obsidian,
поэтому переносится на второй этап фазы 5, когда A и C уже работают и покрыты тестами.
Правило P-API-1 (D-0014) соблюдается: все четыре точки публичны, DOM-вмешательство не требуется.

### 2.4. Q-36 = A: автосоздание соседа через модалку с необязательным именем

Порядок действий при нажатии «следующая глава», если соседа нет:

1. Плагин вычисляет родительский объект (значение `sequential_parent` текущей главы) и новый `order` (§2.2).
2. Открывается модалка с полями, выведенными по §3.4, где `order` предзаполнен и доступен для правки,
   а `title` / `chapter_label` пусты.
3. Пользователь может оставить имя пустым — тогда `title` вычисляется из `title_template` (§2.1).
4. Создание выполняется через единый сервис записи: генерация ULID, имя файла по ADR-0002,
   заполнение системного контракта, валидация, запись.
5. Ссылка нормализуется к каноническому виду (v1.1 §11.3).

**Задел:** необязательное поле `Automation.require_confirmation: boolean` (по умолчанию `true`).
Введение быстрого режима без модалки — аддитивное изменение, отложено до проверки востребованности.

Отклонённый вариант B (создавать сразу по шаблону): при случайном клике в хранилище появляется файл
без явного подтверждения, что противоречит принципу S6.

## 3. Изменения метамодели

### 3.1. Новые поля `ObjectType`

| Поле | Тип | Обяз. | Ограничения |
|---|---|---|---|
| `sequential_parent` | ссылка на `Property` | нет | Только парой с `sequence_key`. Свойство должно иметь `value_type: reference`, `cardinality` ∈ {`1`, `0..1`} |
| `sequence_key` | ссылка на `Property` | нет | Только парой с `sequential_parent`. Свойство должно иметь `value_type: number`, `cardinality: 1` |
| `sequence_step` | number | нет | По умолчанию `10`, > 0 |
| `sequence_direction` | enum | нет | `ascending` \| `descending`, по умолчанию `ascending` |
| `title_template` | text | нет | Плейсхолдеры `{key}` подставляют значения свойств объекта |

Все поля **необязательны**: тип, не являющийся последовательностью, их не имеет.

### 3.2. Новое поле `Property`

| Поле | Тип | Обяз. | Ограничения |
|---|---|---|---|
| `unique_within` | ссылка на `Property` | нет | Должно указывать на свойство того же типа, присутствующее в эффективном наборе. Значение — область действия уникальности |

Это **первое межобъектное ограничение** в модели: все предыдущие правила проверяли один объект
или разрешение ссылки. Реализация требует индекса «значение области → объекты», который строится
при загрузке и поддерживается по событиям файлового API.

### 3.3. Новые поля `Automation`

| Поле | Тип | Обяз. | Семантика |
|---|---|---|---|
| `form_fields` | список ссылок на `Property` + `sys`-поля | нет | Сужение и порядок полей формы. Пусто — выводятся все обязательные |
| `defaults` | словарь | нет | Значения по умолчанию; поддерживаются плейсхолдеры `{next_sequence}`, `{parent}`, `{today}` |
| `require_confirmation` | boolean | нет | По умолчанию `true`. Задел, в MVP не используется |

`sys`-поля адресуются как `sys:title`, `sys:status` и т.д. — это поля системного контракта,
а не объекты `Property` (согласуется с решением v1.1 §14.2 и ADR-0003 §3: `title` — системный атрибут,
а не обычное свойство).

### 3.4. Форма создания выводится, отдельный тип не вводится

```
поля формы     = effective properties типа (алгоритм ADR-0008 §3.3)
                 ∩ Automation.form_fields, если задан
порядок        = Automation.form_fields, иначе порядок в ObjectType.properties
обязательность = Property.required с учётом property_overrides и аспектов
контрол        = по Property.value_type и cardinality
кандидаты      = по Property.target_types / target_facet
значения       = Automation.defaults, иначе пусто
```

**Отклонено: тип `Form`.** Он дублировал бы данные, уже имеющиеся в типе объекта и в определениях
свойств, — нарушение принципа «один факт — одно место», применённого ранее четыре раза.

### 3.5. Отклонено: 13-й тип M1 `Sequence`

Последовательность полностью определяется парой полей на `ObjectType`; отдельный объект дублировал бы их.
Шаг и направление сортировки стали атрибутами `ObjectType` (§3.1) — этого достаточно.

## 4. Правила валидации (переведены из ожидающих в нормативные)

| ID | Уровень | Правило | Сообщение |
|---|---|---|---|
| `sequence.r1` | error | `sequential_parent` и `sequence_key` заданы только парой | «Тип {title} объявлен последовательностью частично: укажите оба поля или ни одного» |
| `sequence.r2` | error | `sequential_parent` — свойство с `value_type: reference` и `cardinality` ∈ {`1`, `0..1`} | «Свойство {key} непригодно как родитель последовательности» |
| `sequence.r3` | error | `sequence_key` — свойство с `value_type: number` и `cardinality: 1` | «Свойство {key} непригодно как ключ порядка» |
| `sequence.r4` | error | Объект типа-последовательности имеет непустое значение `sequence_key` | «Не заполнен ключ порядка {key} у объекта {title}» |
| `sequence.r5` | warn | Разрыв нумерации между соседями | «Между {a} и {b} пропущены значения порядка» |
| `sequence.r6` | error | `sequence_step` > 0 | «Шаг нумерации должен быть положительным» |
| `unique.r1` | error | Пара (`unique_within`, значение свойства) уникальна в хранилище | «В области {значение родителя} уже есть объект с {key} = {значение}: {файл}» |
| `unique.r2` | error | `unique_within` указывает на свойство того же типа из эффективного набора | «Область уникальности {key} не является свойством типа {type}» |
| `meta.r14` | error | Все плейсхолдеры `{key}` в `title_template` соответствуют существующим свойствам типа | «Шаблон заголовка ссылается на несуществующее свойство {key}» |
| `meta.r15` | error | Элементы `Automation.form_fields` разрешимы и принадлежат целевому типу либо являются `sys`-полями | «Форма автоматизации {title} ссылается на поле {факт}, отсутствующее у типа {type}» |

Каталог вырастает с 94 до **104 нормативных правил** (добавлены 10, включая новое `sequence.r6`).

## 5. Обоснование

1. **Объявительность вместо хардкода.** Метамодель не знает о кнопках: она объявляет, что тип является
   последовательностью. Плагин обслуживает любое объявление. Это сохраняет S1 («метамодель как данные»)
   и E3 («всё как знание»), а механизм бесплатно распространяется на `Episode`/`Series`, `Track`/`Album`,
   `Task`/`Project`.
2. **Разделение ключа сортировки и подписи** устраняет лексикографическую сортировку чисел —
   классический дефект, из-за которого «глава 10» идёт раньше «главы 2».
3. **Разреженная нумерация** делает вставку главы локальной операцией без перенумерации.
4. **`unique_within` — общий механизм**, а не частное правило для глав: он сразу покрывает
   `Episode.order` в пределах сериала и `Task.title` в пределах проекта.
5. **Вывод формы вместо отдельного типа** сохраняет ядро из 12 типов и устраняет риск рассинхрона
   между схемой типа и формой ввода.
6. **Поэтапная отрисовка навигации** снижает риск R-07-подобной хрупкости: сначала устойчивые точки API,
   потом CM6-виджеты.

## 6. Последствия

### Положительные
- T1–T5 выполнены без хардкода и без нового типа.
- Механизм переиспользуется для четырёх будущих пар «родитель — последовательность».
- Форма создания и валидация используют один и тот же эффективный набор свойств — расхождение невозможно.

### Отрицательные / стоимость
- **Первое межобъектное ограничение** (`unique.r1`) требует индекса «значение области → объекты»
  и его поддержки по событиям файлового API. Это самый сложный модуль валидатора после разрешения ссылок.
- Алгоритм вычисления `title` из шаблона — ещё один механизм, требующий тестов
  (неизвестный плейсхолдер, пустое значение, нечисловое значение для `{order}`).
- `ObjectType` получил 5 новых необязательных полей; описание типа по `ENTITY_TEMPLATE` стало длиннее.
- Навигация в Live Preview отложена: в режиме правки кнопок в теле заметки в MVP не будет
  (будут в режиме чтения и в панели плагина).

### Что становится возможным позже
- `Automation.require_confirmation: false` — быстрый режим создания.
- Виджеты навигации в Live Preview (CM6) и блок ```` ```sb-nav ````.
- Drag-and-drop переупорядочивание соседей с пересчётом `order`.
- Обобщение `unique_within` до составной области (список свойств) — аддитивно.

## 7. Миграция

- Требуется: нет (определений M1 и объектов M0 в хранилище нет).
- Зафиксировано: все новые поля необязательны, поэтому существующие определения останутся валидными
  после обновления схемы.
