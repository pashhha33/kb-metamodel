# Заметки по реализуемости: Obsidian API и заимствования из Exocortex

> Документ создан по правилу «код на раннем этапе допустим только для проверки реализуемости идей».
> Кода нет — есть проверка публичного API по официальным типам `obsidian.d.ts` (306 430 байт,
> скачаны из `github.com/obsidianmd/obsidian-api`, ветка `master`).
> Все утверждения ниже снабжены источником. Это защита от риска R-05.

---

## 1. Ключевой вывод

**Разделение «технический ключ / отображаемое имя» — не наша выдумка, а штатный механизм Obsidian
в Bases, подтверждённый публичным API.** Это делает решение ADR-0001 (EN-ключ + RU-`label`)
реализуемым без DOM-вмешательства и внутренних API.

Одновременно: **в панели Properties такого механизма нет**, и публичного API для кастомных
виджетов свойств тоже нет. Значит, русские подписи в панели свойств мы обеспечить не можем —
и не должны пытаться. Это резко сокращает раздел 17 черновика v1.1.

## 2. Доказательства по API

### 2.1. Bases: displayName существует и доступен

| Что найдено | Где в `obsidian.d.ts` | Версия |
|---|---|---|
| `BasesConfigFile.properties?: Record<string, Record<string, any>>` с комментарием «Valid keys for this object currently include: **displayName: string**» | интерфейс `BasesConfigFile` | `@since 1.10.0` |
| `getDisplayName(propertyId: BasesPropertyId): string` | контракт представления Bases | `@since 1.10.0` |
| `registerBasesView(viewId: string, registration: BasesViewRegistration): boolean` | регистрация собственного типа представления Bases | `@since 1.10.0` |
| `BasesPropertyId = \`${BasesPropertyType}.${string}\`` где `BasesPropertyType = 'note' \| 'formula' \| 'file'` | идентификатор свойства с префиксом источника | `@since 1.10.0` |
| `parsePropertyId(propertyId): BasesProperty` | разбор идентификатора свойства | `@since 1.10.0` |
| `BasesQueryResult` с `data` и `groupedData`, `QueryController` | результаты запроса Bases доступны плагину | `@since 1.10.0` |
| `BasesOption { key, type, displayName, shouldHide? }` и `BasesOptionGroup` | настройки в меню представления Bases | `@since 1.10.0`, `shouldHide` — `1.10.2` |

**Что это даёт нам напрямую:**
1. Плагин может **сам записывать** `displayName` в файлы `.base` — то есть генерировать таблицы Bases
   с русскими подписями колонок из поля `label` нашей метамодели. Это «режим View» из аналогии пользователя.
   Документация API прямо подтверждает семантику: `getDisplayName()` возвращает «If the property has been
   renamed by the user in the Base config, that value is returned… otherwise the name with the property
   type prefix removed». То есть подпись хранится в конфигурации Base, а не во frontmatter, — ровно
   разделение «source = ключ, view = подпись».
2. `BasesPropertyId` устроен как `note.publisher` — **префикс источника + локальное имя**. Это ровно та же
   идея, что наш `type_prefix` + `key`, и что `exo__Setting` в Exocortex. Три независимых подтверждения
   одного паттерна.
3. Мы можем зарегистрировать **собственный тип представления Bases** (карточки, канбан) через
   `registerBasesView` — и получать готовые результаты запроса через `BasesQueryResult`, не написав
   ни строк запросного движка. Это закрывает пункт «представления: таблицы, карточки, канбан, запросы»
   из требований к метамодели почти бесплатно.
4. `BasesPropertyType = 'note' | 'formula' | 'file'` подтверждает: Bases читает свойства **из frontmatter**.
   Наш выбор X-01 (Markdown+YAML как источник истины) совместим с Bases напрямую.

**Требуемая минимальная версия Obsidian: 1.10.0.** Это надо зафиксировать в `manifest.json` как `minAppVersion`.

### 2.2. Чего в публичном API НЕТ

| Что искали | Результат | Следствие |
|---|---|---|
| `PropertyWidget` | не найдено | Кастомные виджеты свойств в панели Properties недоступны публично |
| `registerPropertyWidget` | не найдено | — |
| `MetadataEditor` | не найдено | Программного доступа к панели свойств нет |
| `registerWidget` | не найдено | — |
| Подмена имени файла в проводнике | не найдено | Раздел 17 v1.1 (13 адаптеров) нереализуем через публичный API |

**Вывод:** сторонние плагины вроде MetaEdit 1.9.0 («Edit properties with Obsidian's native widgets»)
испольвают недокументированные внутренние механизмы. Для нашего MVP это **неприемлемый риск**:
ломается при каждом обновлении Obsidian, требует DOM-вмешательства и регрессионных тестов на UI.

Отсюда следует архитектурное правило (фиксируется в ADR-0005 на шаге 7 фазы 2):

> **Правило P-API-1.** Плагин использует только публичный API. Собственный UI (модалка свойств,
> панель сущностей, карточки) — единственное место, где отображаются `label`. Панель Properties
> Obsidian остаётся работающей, но показывает EN-ключи и не типизирована нашей схемой.

### 2.3. Что есть и что мы используем

| Возможность | Сигнатура | Зачем нам |
|---|---|---|
| Атомарная правка frontmatter | `fileManager.processFrontMatter(file, fn, options?): Promise<void>` | Единственный правильный способ писать свойства: не ломает остальной файл, атомарен |
| Разрешение ссылки | `metadataCache.getFirstLinkpathDest(linkpath, sourcePath): TFile \| null` | Проверка «цель существует» (валидация ссылок) |
| Файл → текст ссылки | `metadataCache.fileToLinktext(file, sourcePath, omitMdExtension?): string` | Обратная нормализация ссылок |
| Генерация ссылки | `fileManager.generateMarkdownLink(file, sourcePath, subpath?, alias?)` | Каноническая ссылка с учётом настроек пользователя (ADR-0002, п. 4) |
| Ссылки из frontmatter | `CachedMetadata.frontmatterLinks: FrontmatterLinkCache[]` (поля `link`, `original`, `key`, `display`) | **Критично:** кэш сам знает, в каком свойстве лежит ссылка — не надо парсить YAML, чтобы построить граф связей |
| Псевдонимы | `parseFrontMatterAliases(frontmatter): string[] \| null` | ADR-0004 |
| Разбор YAML / frontmatter | `parseYaml`, `parseFrontMatter`, `getFrontMatterInfo` | Загрузка определений M1 |
| Разбор текста ссылки | `parseLinktext(linktext): {path, subpath}` | Извлечение `title` и технической части |
| Родительская папка для нового файла | `fileManager.getNewFileParent(sourcePath, newFilePath?)` | Создание объектов в правильном месте |

**Отдельно важно про `frontmatterLinks`.** Кэш метаданных Obsidian уже отдаёт ссылки из frontmatter
вместе с именем поля (`key`). Это значит, что для построения графа связей и проверки ссылочной
целостности нам **не нужен собственный парсер YAML** — достаточно штатного кэша. Существенная экономия
на самом рискованном модуле MVP.

## 3. Разбор Exocortex: что берём, что не берём

`kitelev/exocortex` — семантическая система знаний на RDF/SPARQL, работает как плагин Obsidian, CLI
и TS-библиотека. Заявляет 11 400+ тестов, покрытие core 95 %. `minAppVersion: 1.5.0`. Установка через BRAT.
Лицензия MIT. Активная разработка (последний коммит на момент проверки — 19.10.2026).

### 3.1. Берём (5 идей)

| # | Идея Exocortex | Как применяем у себя | Ценность |
|---|---|---|---|
| **E1** | **`rdfs:label` как обязательный элемент онтологии.** В `exoas-w3c` есть отдельный *lint report*, проверяющий качество онтологии по наличию `label`, `comment`, `domain/range` | Поле `label` обязательно в каждом определении M1 (ADR-0001). Вводим **отчёт о качестве метамодели** — проверка, что у всех определений заполнены `label`, `definition`, `value_type`, `cardinality` | Прямой ответ на замечание пользователя: «в режиме view видны другие имена» — это и есть `label` |
| **E2** | **Разделение технического имени и человекочитаемого.** Имя файла — UUIDv5 от URI, а `aliases` хранят `rdf:Property`, `owl:Thing` | Наш ADR-0002: имя файла = `title (PREFIX-ULID).md`, идентичность = `id`. Плюс ADR-0004: `aliases` только для реальных псевдонимов | Подтверждает наш выбор независимой реализацией |
| **E3** | **«Everything as Knowledge»** — команды, workflow, схемы свойств, layouts и даже настройки плагина описаны как данные в хранилище, а не зашиты в код | Уже есть в черновиках как S1. Усиливаем: `View` и `Automation` — полноценные объекты M1, а не настройки плагина. Настройки плагина в MVP **не** гомоиконизируем (это уже перебор для нашего масштаба) | Добавление типа не требует перекомпиляции |
| **E4** | **AssetSpaces — модульные онтологии**: доменный словарь поставляется отдельным версионируемым пакетом, монтируется по требованию | Задел: наша метамодель должна быть **экспортируема/импортируема как пакет**. В MVP не реализуем, но требование учитываем в схеме: все определения M1 самодостаточны и ссылаются друг на друга по `id`, а не по путям | Даёт путь к «готовым онтологиям» (кино, книги, проекты) |
| **E5** | **Пространство имён с разделителем** `__`: `exo__Setting`, `exocmd__Command_cliName` | Задел на будущее: если понадобится расширять схему сторонними пакетами, ключи получают вид `sb__title`, `pack__field`. **В MVP не вводим** — избыточно для одного пакета | Дешёвый задел под E4 |

### 3.2. Не берём (4 позиции) — с обоснованием

| # | Что у них | Почему не берём |
|---|---|---|
| **N1** | **Каждая RDF-тройка — отдельный Markdown-файл.** В `exoas-w3c`: 31 828 троек → **37 339 файлов**, имена — UUIDv5 | Это приемлемо для статического корпуса публичных онтологий, который монтируют один раз. Для личной БЗ, где связи создаются ежедневно, это катастрофа: 1000 связей = 1000 файлов, индексация vault деградирует. Наша **гибридная модель** (ссылка в свойстве, а объект `Relation` — только когда у связи есть атрибуты, решение X-03) строго лучше для нашего случая |
| **N2** | **SPARQL как язык запросов** | Полноценный SPARQL-движок — это месяцы работы и тяжёлая зависимость. В MVP достаточно: фильтр по типу + по категории + по значению свойства. Задел сохраняем: наша модель тривиально конвертируется в тройки, поэтому SPARQL можно добавить позже как модуль экспорта |
| **N3** | **OWL/SHACL-валидация как основа** | SHACL — правильный промышленный ответ, но требует RDF-графа в памяти. Наша валидация — декларативные правила поверх JSON Schema + собственные проверки связей. Проще, быстрее, достаточно для MVP |
| **N4** | **ExoSync (синхронизация через GitHub REST), UI/CLI parity, desktop/mobile parity** | Вне рамок MVP по условию пользователя (локально, офлайн, мобильная поддержка не обязательна). CLI как второй клиент не нужен |

### 3.3. Что стоит посмотреть отдельно (не блокирует нас)

- `docs/explanation/settings-homoiconization.md` — как они сделали настройки данными. Полезно, если
  когда-нибудь захотим E3 в полном объёме.
- `docs/explanation/assetspace-sdk-topology.md` — топология пакетов онтологий. Полезно для E4.
- Их `PATTERNS.md` и `ARCHITECTURE.md` — образцы структуры документации крупного проекта на TS.
- **`ARCHITECTURE.md` и `VISION.md`** стоит прочитать перед фазой 5 (архитектура плагина) — но как
  референс по организации кода, а не по метамодели.

### 3.4. Существенное отличие целей

| | Exocortex | Second Brain (наш проект) |
|---|---|---|
| Основа | RDF-тройки, SPARQL, OWL | Markdown + YAML frontmatter, собственный валидатор |
| Хранение связи | отдельный файл на тройку | ссылка в свойстве; объект `Relation` только при наличии атрибутов |
| Цель | семантическая совместимость и логический вывод | практичная личная БЗ с валидацией и удобными представлениями |
| Зависимости | тяжёлое ядро, CLI, GitHub-sync | только Obsidian API ≥ 1.10.0 |

**Вывод:** Exocortex — доказательство, что подход «метамодель как данные» работает в Obsidian
в промышленном масштабе. Но его цена (37 339 файлов на корпус онтологий, SPARQL-движок) для личной
базы избыточна. Мы берём у него **семантику имён** (E1, E2, E5) и **принцип данных** (E3, E4),
а не его физическую модель хранения.

## 4. Влияние на план

| Пункт | Действие |
|---|---|
| `minAppVersion` | Зафиксировать `1.10.0` в `manifest.json` (нужен публичный API Bases) |
| Раздел 17 v1.1 (13 адаптеров UI) | **Вывести из MVP целиком.** Причина: подмена имени файла недоступна через публичный API, а ADR-0002 устранил потребность. Риск R-07 снят |
| Раздел 18 v1.1 (своя модалка свойств) | Оставить, но как **основной и единственный** типизированный ввод. Панель Properties остаётся «свободным» путём с последующей валидацией — ровно как описано в v1.1 §18.5 |
| Граф связей | Строить на `CachedMetadata.frontmatterLinks` — без собственного парсера YAML |
| Представления (таблицы, карточки, канбан) | Реализовывать через `registerBasesView` + `BasesQueryResult`, а не собственным движком |
| Bases как источник истины | **Нет.** Bases — представление. Источник истины — frontmatter (X-01 подтверждён технически: `BasesPropertyType = 'note'`) |
| Отчёт о качестве метамодели | Добавить как артефакт фазы 3 (по образцу lint report из `exoas-w3c`) |
