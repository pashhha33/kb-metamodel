# `MediaAsset`: механизм создания и поведение — разбор

> **Статус:** `actual`. Предложение принято пользователем и зафиксировано в **ADR-0011**.
> Раздел 3 — факты, проверенные по `obsidian.d.ts`. Разделы 6–7 описывают варианты и проект решения;
> **нормативная редакция — в ADR-0011**, при расхождении приоритет у ADR.
>
> **Изменения против первоначальной рекомендации ассистента:** Q-42 принят в варианте **B**
> (`MediaAsset.galleries`, порядок не хранится) вместо рекомендованного A (`Gallery.items`).
> Обоснование пользователя: порядок не свойство галереи, а свойство представления (Bases сортирует).
> Это согласовано с ADR-0005 §3.1 (ссылки только вверх) и ADR-0009 §3.1 (разделение — задача
> представления) и растворяет пробел G-15.

### 3.3. Архитектурное следствие: единый `MediaResolver`

T6, T7, T8 и T14 выполняют **одну и ту же операцию**: по обёртке получить изображение, либо по
изображению найти обёртку. Четыре независимые реализации неизбежно разъедутся. Требуется один модуль:

```
MediaResolver
  byAsset(id | TFile)   → { asset, file, resourcePath }   // T7, T8, T14
  byImageFile(path)     → MediaAsset | null               // T6: привязано ли изображение
  reverseIndex          → Map<filePath, MediaAsset>       // инвалидация по событиям vault
```

Правила модуля (из v1.1 §10.3, становятся нормативными):

1. Разрешение **не изменяет** обёртку и её метаданные.
2. При отсутствии результата — **сообщить, не выбирать произвольное изображение**.
3. Разрешение по стабильному `id`, а не по совпадению строк названия (ADR-0002).
4. Индекс не является источником истины: источник — поле `file` в обёртках (X-01).

## 5. Ключевой структурный вопрос: кто владеет связью

`MediaAsset` **уже является реификацией**: сырой файл — это «простая ссылка», а обёртка существует
именно потому, что у связи файла с объектом есть атрибуты (роли, источник, автор, лицензия).
Это прямое следствие «правила повышения» X-03.

Следовательно, добавлять `Relation` поверх обёртки — **реифицировать дважды**. Для личной базы
с сотнями обложек это сотни файлов-связок: паттерн N1 из Exocortex (31 828 троек → 37 339 файлов),
отклонённый решением D-0016.

| Вариант | Кто владеет связью | Запрос «обложка книги» | Новых механизмов |
|---|---|---|---|
| A | Обёртка: `targets: [Book…]` + `roles` | поиск по индексу среди всех обёрток | индекс + алгоритм разрешения + правило приоритета |
| B | `Relation` с атрибутом роли | чтение связи; файл на каждое размещение | `RelationType` на каждую роль + взрыв числа файлов |
| **C** ⭐ | **Объект, через свойство**: `Book.cover` → `MediaAsset` | **чтение свойства** | **ноль** — используется ADR-0003 |

**Рекомендация C подтверждается видением пользователя**: T8 формулирует запрос именно как
«из поля `cover` объекта `book` подставить изображение обёртки» — то есть как чтение свойства.

Побочные выигрыши C:

1. Роль выражается **именем свойства** (`cover`, `portrait`, `logo`), а `roles` обёртки служит
   фильтром кандидатов: для `Book.cover` с `expected_media_role: cover` предлагаются только обёртки,
   у которых `cover` входит в `roles`.
2. «Одно изображение в двух ролях» работает естественно: два свойства указывают на одну обёртку.
3. G-8 и неоднозначность почти исчезают: у свойства одно значение или упорядоченный список.
4. Колонка в Bases появляется сама: `note.cover` — свойство frontmatter.

**Что теряем против v1.1 §10:** «динамическое разрешение без записи». Потеря мнимая — v1.1 §10.3
запрещал **копирование метаданных** обёртки в объект, а не хранение ссылки.

## 6. Вопросы и рекомендации

### Q-41. «Метод создания»: фасет классификации или enum-свойство?

T9 требует, чтобы «генерация ИИ» была **триггером дополнительных свойств**. Это ровно механизм
`Aspect` из ADR-0008 — но `Aspect` активируется **категориями** (`trigger_categories`).

| Вариант | Механизм | Плюсы | Минусы |
|---|---|---|---|
| **A** ⭐ | Фасет `Creation method` (`key: creation_method`) с категориями «Фото», «Коллаж», «Рисунок», «Генерация ИИ»; назначение в `cat_creation_method`; аспект `ai_generation` с `trigger_categories: [Генерация ИИ]` | **Ноль новых механизмов** — ADR-0007 и ADR-0008 применяются как спроектированы. Иерархия возможна («Генерация ИИ» → «Stable Diffusion» → «SDXL»). Расширяется пользователем без изменения схемы. Мульти-выбор поддерживается кардинальностью фасета | На три объекта M1 больше (таксономия, фасет, категории) |
| B | Enum-свойство `creation_method: photo \| collage \| drawing \| ai_generated` | Одно поле, проще | Для триггера требуется **активировать отложенное расширение** `Aspect.trigger_conditions` (ADR-0008 §3.6). Нет иерархии. Расширение списка = изменение схемы |
| C | Свободный текст | Дешевле всего | Нет ни валидации, ни триггера — T9 невыполнимо |

**Рекомендация: A.** Это второй реальный случай применения `Aspect` после профессии — хорошая проверка
того, что механизм спроектирован верно, а не под одну задачу.

Пример активируемых свойств для «Генерация ИИ»: `prompt`, `negative_prompt`, `model`, `seed`,
`sampler`, `steps`, `source_image` (ссылка на другую обёртку — производное изображение).

### Q-42. `Gallery`: включать в ядро MVP и кто владеет порядком?

T11 требует привязку к одной или нескольким галереям. Тип `Gallery` сейчас в списке отложенных.

| Вариант | Механизм | Плюсы | Минусы |
|---|---|---|---|
| **A** ⭐ | `Gallery` — 9-й конкретный тип (ветка `Collection`, префикс `GALLERY` уже зарезервирован). Состав и порядок хранятся в **`Gallery.items: [MediaAsset…]`** — упорядоченный список | Порядок выражен позицией в списке (соглашение уже принято в Q-40 = B). Один факт — одно место: галерея владеет своим составом. Изображение в трёх галереях имеет три независимые позиции. Структура повторяет `ObjectType.properties` | Конкретных типов MVP становится 9; для вставки в середину списка нужна операция плагина |
| B | Привязка на стороне обёртки: `MediaAsset.galleries: [Gallery…]` | Обёртка знает свои галереи | **G-15 не решается**: порядок в каждой галерее невыразим. Либо вложенная структура (запрещена ограничением панели Properties), либо параллельные списки (хрупко) |
| C | Галерея как фасет классификации | Ноль новых типов | Фасет не имеет ни описания, ни порядка, ни обложки; галерея — это кураторская подборка, а не значение оси |
| D | `Relation` между галереей и обёрткой с атрибутом `order` | Порядок выражен точно | Взрыв числа файлов: 10 галерей × 50 изображений = 500 связей |

**Рекомендация: A.** Механизм последовательностей из ADR-0010 здесь **не применяется намеренно**:
он требует одного родителя (`sequential_parent`), а изображение входит в несколько галерей.
Порядок вместо этого выражается позицией в списке `Gallery.items`.

### Q-43. Источники изображения при создании: какие включать в MVP?

| Источник | API | Вердикт |
|---|---|---|
| Непривязанные изображения хранилища | `Vault.getFiles()` + индекс | ✅ включать |
| Буфер обмена | `navigator.clipboard.read()` + `Vault.createBinary`, либо перехват `editor-paste` | ⚠️ включать **с прототипом**; устойчивый запасной путь — поле вставки в модалке |
| Путь к файлу на диске | Node `fs` + `getAvailablePathForAttachment` | ⚠️ включать как **desktop-only**, изолированно; помечать в README |
| URL в сети | `fetch` + `Vault.createBinary` | ❌ **конфликтует с рамкой «локально и офлайн, без внешних API»** |

| Вариант состава | Плюсы | Минусы |
|---|---|---|
| A: все четыре, включая URL | Максимальное удобство | Нарушает рамку MVP; нужны обработка сетевых ошибок, кэш, вопросы лицензии и авторства; офлайн-режим перестаёт быть гарантией |
| **B** ⭐: три (хранилище, буфер, диск), URL отложен | Покрывает все офлайн-сценарии; рамка MVP не нарушена | Изображение из интернета нужно сначала скачать браузером |
| C: два (хранилище, буфер) | Минимум риска | Путь на диске — частый случай для отобранных обложек |

**Рекомендация: B.** Задел: источник `url` добавляется позже как отдельный `Automation` с явной
пометкой «требует сети» — аддитивно, без изменения модели.

### Q-44. Переименование файла изображения (T12)

| Вариант | Правило | Плюсы | Минусы |
|---|---|---|---|
| **A** ⭐ | Имя файла изображения = `{title} ({MEDIA}-{id}).{ext}` — конвенция ADR-0002, распространённая на бинарные файлы. Переименование **только при создании и по явной команде**, не при каждой правке `title` | Стабильность: техническая часть `(MEDIA-{id})` не меняется, поэтому ссылки не ломаются. Единообразие с заметками. `renameFile` сам обновляет ссылки | Редактирование `title` не синхронизирует имя файла автоматически → возможна визуальная рассинхронизация, устраняется командой |
| B | Переименовывать при каждом изменении `title` | Имя всегда соответствует | Каждая правка названия = переименование файла + обновление всех ссылок во всём хранилище; дорого и опасно |
| C | Не переименовывать вообще, хранить исходный путь в `file` | Ноль операций | Противоречит T12; исходные имена вида `IMG_4821.jpg` не несут смысла |

**Рекомендация: A** с тремя уточнениями, закрывающими G-14:

1. **Расширение сохраняется** из исходного файла (`jpg`, `png`, `webp`, `avif`).
2. **Усечение `title`** до 60 символов — как в ADR-0002; полный `title` во frontmatter обёртки.
3. **Коллизия имён** разрешается через `getAvailablePathForAttachment`, а не счётчиком вручную.

## 7. Проект решения (нормативным станет после ADR-0011)

### 7.1. Поля `MediaAsset`

| Поле | Тип | Обяз. | Кардинальность | Описание |
|---|---|---|---|---|
| `file` | ссылка на файл хранилища | **да** | `1` | Единственная ссылка на физический файл |
| `media_kind` | enum | да | `1` | `image` \| `audio` \| `video` \| `document` |
| `roles` | enum (множественный) | нет | `0..n` | **T10:** роли, которые обёртка способна выполнять. Используется как фильтр кандидатов |
| `cat_creation_method` | список ссылок на `Category` | нет | по фасету | **T9 / Q-41 = A:** метод создания; активирует аспекты |
| `source_url` | text | нет | `0..1` | Откуда взято (справочно, не для загрузки) |
| `author` | reference → `Person` \| `Organization` | нет | `0..1` | Автор |
| `license` | text | нет | `0..1` | Лицензия |
| `description` | text | нет | `0..1` | Описание |

Поле `role` (единственное число) **переименовывается в `roles`** с изменением кардинальности —
это изменение фиксируется в `NAME_MAPPING.md` по политике D-0008.

**Не хранятся:** ширина, высота, пропорции, размер файла (G-11). Читаются по требованию и кэшируются
в `.sb/cache/` с инвалидацией по событиям файлового API. Обоснование: принцип X-01 — один источник истины.

### 7.2. Связь с объектами (Q-37 = C)

Через обычные свойства объектов:

| Тип | Свойство | `expected_media_role` | Кардинальность |
|---|---|---|---|
| `Book` | `cover` | `cover` | `0..1` |
| `Person`, `Character` | `portrait` | `portrait` | `0..1` |
| `Organization` | `logo` | `logo` | `0..1` |
| `Book` | `illustrations` | `preview` | `0..n` |
| `Gallery` | `items` | — (состав, а не роль) | `0..n`, **порядок значим** |

Новое необязательное поле `Property.expected_media_role` (enum `role`) — фильтр кандидатов.

Обратный список «какие объекты используют обёртку» **вычисляется** из `MetadataCache`
(`embeds`, `frontmatterLinks`, `resolvedLinks`), а не хранится.

### 7.3. Аспект метода создания (T9, Q-41 = A)

```yaml
---
type: aspect
title: ai_generated_media
label: Генерация ИИ
trigger_categories:
  - "[[Генерация ИИ (CAT-01J8Z6…)|Генерация ИИ]]"
properties:
  - "[[prompt (PROP-…)|Промпт]]"
  - "[[model (PROP-…)|Модель]]"
  - "[[seed (PROP-…)|Seed]]"
  - "[[source_image (PROP-…)|Исходное изображение]]"
is_active: true
---
```

Активация включает потомков категории (ADR-0008 §3.2), поэтому подкатегория «Stable Diffusion»
также активирует аспект.

### 7.4. Механизм создания (плагин)

1. Явное действие пользователя: команда палитры, пункт контекстного меню на файле (`editor-menu`),
   кнопка у изображения (T6) или «создать обёртку» из модалки свойства.
2. Модалка с тремя шагами, форма выводится по ADR-0010 §3.4:
   - **источник** (Q-43 = B): непривязанные изображения хранилища (**миниатюры**, T14) /
     буфер обмена / путь на диске;
   - **имя обёртки** (T12) и роли (`roles`, мульти-выбор, T10);
   - **метаданные**: `media_kind`, метод создания, `source_url`, `author`, `license`, `description`.
3. При выборе источника вне хранилища файл копируется в хранилище через
   `getAvailablePathForAttachment` + `createBinary`.
4. Файл изображения переименовывается по Q-44 = A.
5. Генерация ULID, имя файла обёртки по ADR-0002, заполнение системного контракта, валидация, запись.
6. Если вызов произошёл из свойства объекта — обёртка сразу записывается в это свойство,
   а `roles` предзаполняется из `expected_media_role`.

**Критерий необходимости обёртки (Q-38 = B):** обёртка создаётся, когда изображению нужна **роль**
или **собственные метаданные** (источник, автор, лицензия, метод создания). Иллюстрации внутри текста
заметки остаются обычными `![[file.png]]` и обёртки не требуют.

### 7.5. Правила безопасности (из v1.1 §10.3, нормативные)

1. Предпочтительна **ссылка** на обёртку, а не копирование её данных в объекты.
2. Автоматическое копирование метаданных **не выполняется в MVP** (Q-39).
3. При отсутствии подходящего изображения плагин **сообщает** об этом и не выбирает произвольное.
4. Разрешение запроса **не изменяет** обёртку и её метаданные.
5. Удаление, архивирование цели или изменение ролей учитывается проверками целостности.
6. Обёртка, на которую ссылается архивный объект, остаётся валидной (ADR-0009: ссылки на архив не ломаются).

### 7.6. Правила целостности (`media.*`)

| ID | Уровень | Правило |
|---|---|---|
| `media.r1` | error | `file` присутствует и указывает на существующий файл хранилища |
| `media.r2` | error | `media_kind` и каждое значение `roles` входят в соответствующие enum |
| `media.r3` | warn | Обёртка-сирота: на неё нет ссылок ни одного объекта |
| `media.r4` | warn | Свойство с `expected_media_role: X` ссылается на обёртку, у которой `X` не входит в `roles` |
| `media.r5` | warn | Несколько обёрток указывают на один `file` — вероятно, дубль |
| `media.r6` | info | Файл вложения не имеет обёртки (норма для иллюстраций в тексте, Q-38 = B) |
| `media.r7` | error | `Gallery.items` содержит дубликаты или неразрешимые ссылки |
| `media.r8` | warn | Изображение входит более чем в 5 галерей — проверьте обоснованность |

Каталог вырастет со 104 до **112 правил**.
