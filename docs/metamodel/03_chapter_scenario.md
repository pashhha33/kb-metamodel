# Сценарий «Глава»: предложение по доработке метамодели

> **Статус:** `actual`. Предложение принято пользователем и зафиксировано в **ADR-0010**.
> Раздел 3 ниже описывает предложение в первоначальном виде; нормативная редакция полей —
> в ADR-0010 §3 (добавлены `sequence_step`, `sequence_direction`, `require_confirmation`).

---

## 1. Требование пользователя (дословно, разобрано на пункты)

| # | Требование | Природа |
|---|---|---|
| T1 | `Chapter` привязан к `Book` через свойство | **M1** — связь и её кардинальность |
| T2 | Данные для создания: запрос или ввод в модалке — объект привязки, номер главы, имя главы | **M1** (состав полей) + **плагин** (форма создания) |
| T3 | В теле заметки — кнопки перехода на соседние главы и на родительский объект | **плагин** (отрисовка) + **M1** (объявление последовательности) |
| T4 | При отсутствии соседней главы нажатие кнопки создаёт её с запросом имени | **плагин** (автоматизация) + **M1** (правило нумерации) |
| T5 | Имя можно пропустить — тогда именем выступает номер главы: «Глава N» | **M1** — шаблон заголовка по умолчанию |

**Ключевой вывод:** требование смешивает два уровня. T1, T5 и части T2–T4 относятся к метамодели;
отрисовка кнопок и модалка — к плагину (фаза 5). Разделение обязательно, иначе повторится ошибка
черновика v1.1, где ~60 % текста метамодели составляло описание реализации (C-36).

**Почему это нельзя захардкодить.** Если плагин будет «знать», что у `Chapter` есть `Book`-родитель
и кнопки «предыдущая/следующая», мы нарушим сильное решение S1 («метамодель как данные») и идею E3
из Exocortex («всё как знание»). Правильная формулировка: **метамодель объявляет, что тип является
упорядоченной последовательностью внутри родителя, а плагин умеет обслуживать любое такое объявление.**

Тогда тот же механизм бесплатно покрывает:

| Тип | Родитель | Ключ порядка |
|---|---|---|
| `Chapter` | `Book` | номер главы |
| `Episode` | `Series` | номер эпизода |
| `Track` | `Album` | номер трека |
| `Task` | `Project` | порядок выполнения |

## 2. Чего в модели сейчас нет: четыре пробела

| ID | Пробел | Почему блокирует требование |
|---|---|---|
| **G-1** | Нет способа объявить «тип является упорядоченной последовательностью внутри родителя» | Без этого плагин не может найти «соседние главы»: он не знает, какое свойство — родитель, а какое — порядок. Кнопки (T3) и автосоздание (T4) невозможны без хардкода |
| **G-2** | Нет **уникальности в области действия** (scoped uniqueness). Нужно: пара (`part_of`, `order`) уникальна — две главы с одним номером в одной книге недопустимы | Это первое **межобъектное** ограничение в нашей модели. Все 89 правил из `RULES.md` проверяют либо один объект, либо разрешение ссылки. Без scoped uniqueness нумерация глав разъезжается молча |
| **G-3** | Нет шаблона заголовка по умолчанию | T5 требует: если имя пропущено → «Глава N». Сейчас `contract.r6` требует непустой `title`, но способ его получить не определён. Без шаблона правило придётся хардкодить |
| **G-4** | Нет определения формы создания | T2 требует модалку с тремя полями в определённом порядке. `Automation` имеет `trigger`, `mechanism`, `target_types`, но не описывает, какие поля спрашивать и с какими значениями по умолчанию |

## 3. Предложение: пять необязательных полей, ни одного нового типа

Все поля **необязательные** и добавляются к существующим типам. Ядро M1 остаётся **12 типов** —
13-й тип не вводится намеренно (см. §3.6).

### 3.1. G-1 → объявление последовательности на `ObjectType`

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D5A1
type: object_type
title: chapter
label: Глава
type_prefix: CHAP
is_abstract: false
layer: domain
parent_type: "[[Work (OTYPE-01J8Z6…)|Work]]"

properties:
  - "[[part_of (PROP-01J8Z6…)|Часть произведения]]"
  - "[[order (PROP-01J8Z6…)|Порядковый номер]]"
  - "[[chapter_label (PROP-01J8Z6…)|Обозначение главы]]"

# ── объявление последовательности (G-1) ──────────────────
sequential_parent: "[[part_of (PROP-01J8Z6…)|Часть произведения]]"
sequence_key: "[[order (PROP-01J8Z6…)|Порядковый номер]]"
title_template: "Глава {order}"
---
```

| Поле | Тип | Обяз. | Семантика |
|---|---|---|---|
| `sequential_parent` | ссылка на `Property` | нет | Свойство, указывающее на родителя последовательности. Должно иметь `value_type: reference` и `cardinality: 1` или `0..1` |
| `sequence_key` | ссылка на `Property` | нет | Свойство, упорядочивающее соседей. Должно иметь `value_type: number` |
| `title_template` | text | нет | Шаблон `title` при создании без явного имени. Плейсхолдеры `{key}` подставляют значения свойств объекта |

Оба поля задаются **только парой**: `sequential_parent` без `sequence_key` (и наоборот) — `error`.

Что это даёт плагину (без хардкода):
- «предыдущая/следующая» = сосед по `sequence_key` среди объектов с тем же `sequential_parent`;
- «к родительскому объекту» = переход по значению `sequential_parent`;
- «создать следующую» = новый объект того же типа с `sequence_key = max + step` и тем же родителем;
- заголовок по умолчанию = `title_template` с подстановкой.

### 3.2. G-2 → уникальность в области действия на `Property`

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D5A2
type: property
title: order
label: Порядковый номер
value_type: number
cardinality: 1
required: true
scope: specific
unique_within: "[[part_of (PROP-01J8Z6…)|Часть произведения]]"   # ← G-2
definition: Номер главы в пределах произведения. Используется для порядка и для заголовка по умолчанию.
---
```

`unique_within` — ссылка на другое свойство того же типа, значение которого задаёт область уникальности.
Правило `unique.r1`: **пара (значение `unique_within`, значение свойства) уникальна в хранилище.**

Механизм общий, поэтому сразу покрывает будущие случаи:

| Тип | Свойство | Область уникальности |
|---|---|---|
| `Chapter` | `order` | `part_of` (книга) |
| `Episode` | `order` | `part_of` (сериал) |
| `Task` | `title` | `part_of` (проект) |

### 3.3. G-3 → шаблон заголовка

Правило `contract.r6` («`title` не пуст») **не отменяется**. Меняется способ получения значения
**при создании**:

1. Пользователь ввёл имя → оно становится `title`.
2. Пользователь оставил имя пустым → плагин вычисляет `title` из `ObjectType.title_template`.
3. `title_template` не задан и имя пустое → `error`, создание не выполняется.

Для «Глава {order}» при `order: 7` получается `title: Глава 7`, имя файла
`Глава 7 (CHAP-01J8Z6….md)`. Требование T5 выполнено, `contract.r6` не нарушено.

Плейсхолдеры: `{key}` — значение свойства с таким `key`. Неизвестный плейсхолдер → `error`
при загрузке метамодели (правило `meta.r14`), а не при создании объекта.

### 3.4. G-4 → форма создания выводится из типа, а не описывается отдельно

**Отдельный тип `Form` не вводится.** Форма создания **выводится** из уже имеющихся данных:

```
поля формы = effective properties типа (алгоритм ADR-0008 §3.3)
порядок    = порядок в ObjectType.properties
обязательность = Property.required (с учётом overrides)
контрол    = по Property.value_type и cardinality
кандидаты  = по Property.target_types / target_facet
```

`Automation` получает одно необязательное поле-уточнение:

```yaml
---
id: 01J8Z6M4K2Q7V9X3N5B0C1D5A3
type: automation
title: create_chapter
label: Создать главу
trigger: manual
mechanism: custom
target_types:
  - "[[Глава (OTYPE-01J8Z6…)|Глава]]"
form_fields:                       # ← необязательное сужение и порядок
  - "[[part_of (PROP-01J8Z6…)|Часть произведения]]"
  - "[[order (PROP-01J8Z6…)|Порядковый номер]]"
  - "[[title (sys)|Имя главы]]"
defaults:
  order: "{next_sequence}"
is_active: true
---
```

| Поле | Семантика |
|---|---|
| `form_fields` | необязательный список: какие поля спрашивать и в каком порядке. Пусто — выводятся все обязательные |
| `defaults` | необязательные значения по умолчанию; поддерживаются служебные плейсхолдеры `{next_sequence}`, `{parent}` |

`title` в `form_fields` адресуется как `sys` — это поле системного контракта, а не объект `Property`
(согласуется с ADR-0003 §3 и решением v1.1 §14.2: `title` — системный атрибут, а не обычное свойство).

### 3.5. Отрисовка кнопок (T3, T4) — уровень плагина, не метамодели

Проверка публичного API (`obsidian.d.ts`):

| Механизм | Публичный | Версия | Пригодность |
|---|---|---|---|
| `registerMarkdownPostProcessor` | ✅ | `@since 0.9.7` | Панель навигации в **режиме чтения** — устойчиво, рекомендуется для MVP |
| `registerMarkdownCodeBlockProcessor` | ✅ | `@since 0.9.7` | Блок ```` ```sb-nav ```` в теле — явно, управляемо, работает и в чтении |
| `registerEditorExtension` (CodeMirror 6) | ✅ | `@since 0.12.8` | Виджет в **Live Preview** — сложнее, требует тестов на обновлениях Obsidian |
| `registerView` | ✅ | — | Отдельная панель плагина — самый устойчивый вариант |

Правило P-API-1 (D-0014) соблюдается: все четыре точки публичны. DOM-вмешательство не требуется.

**Рекомендация для MVP:** режим чтения через `registerMarkdownPostProcessor` + код-блок ```` ```sb-nav ````
для явного размещения. Live Preview — отдельным этапом после проверки устойчивости.

Метамодель при этом **не знает о кнопках**. Она знает только «тип является последовательностью»
(§3.1). Отрисовка — поведение плагина.

### 3.6. Почему не вводится 13-й тип

Рассмотрено и отклонено: тип `Sequence` (объект, описывающий последовательность как сущность).

| Аргумент | |
|---|---|
| Против | Последовательность не существует отдельно от типа и его свойства: она полностью определяется парой (`sequential_parent`, `sequence_key`). Отдельный объект дублировал бы эти данные — нарушение принципа «один факт — одно место», применённого трижды |
| Против | Ядро уже содержит 12 типов и 89 правил. Каждый новый тип — это описание по `ENTITY_TEMPLATE`, ветка в JSON Schema, набор тестов |
| За (слабый) | Можно было бы задать шаг нумерации и направление сортировки на объекте |
| Решение | Шаг и направление — атрибуты `ObjectType` (`sequence_step`, `sequence_direction`), если понадобятся. Аддитивно |

## 4. Правила валидации, добавляемые сценарием

| ID | Уровень | Правило |
|---|---|---|
| `sequence.r1` | error | `sequential_parent` и `sequence_key` заданы только парой |
| `sequence.r2` | error | `sequential_parent` указывает на `Property` с `value_type: reference` и `cardinality` ∈ {`1`, `0..1`} |
| `sequence.r3` | error | `sequence_key` указывает на `Property` с `value_type: number` и `cardinality: 1` |
| `sequence.r4` | error | Объект-последовательность имеет непустое значение `sequence_key` |
| `sequence.r5` | warn | Обнаружен разрыв нумерации (пропущенное значение между соседями) |
| `unique.r1` | error | Пара (`unique_within`, значение свойства) уникальна в хранилище |
| `unique.r2` | error | `unique_within` указывает на свойство того же типа, присутствующее в эффективном наборе |
| `meta.r14` | error | Все плейсхолдеры `{key}` в `title_template` соответствуют существующим свойствам типа |
| `meta.r15` | error | Все элементы `Automation.form_fields` разрешимы и принадлежат целевому типу (или являются `sys`-полями) |

Итого каталог вырастет с 89 до **98 правил**.
