# Реестр исходных документов

Черновики в `inbox/` остаются **read-only** (D-0006): правка в них не вносится. Поэтому авторитетные
статусы, отношения замены и сведения о недействительных идентификаторах фиксируются в этом реестре.

**Разрешение противоречия приоритетов (C-38).** В черновиках документ с более ранними решениями
(Спецификация) был помечен `утверждён`, а документ с более поздними (v1.1) — `черновик`. Авторитетным
источником с 2026-10-21 является **не черновик, а набор ADR**:

```
docs/adr/ADR-0001…ADR-0011   (accepted)  ← авторитет
docs/metamodel/00_overview.md            ← сводное описание
docs/validation/RULES.md                 ← правила
inbox/**                                 ← историческое сырьё, read-only
```

Правило на будущее: при расхождении любого документа с принятым ADR приоритет у ADR.

## 3. Недействительные идентификаторы (C-04, C-05)

Идентификаторы в черновиках **недействительны** и не подлежат переносу. Причина не в конкретных
значениях, а в самом формате: последовательный счётчик `КОДТИПА-000001` требует централизованной
выдачи номеров, а в примерах черновиков номера присваивались произвольно.

| ID в черновиках | Что обозначал | Проблема |
|---|---|---|
| `DOC-000002` | одновременно «Метамодель v1.0» и «Метамодель v1.1» | Нарушение уникальности (C-04) |
| `OBJECT-TYPE-000001` | «Книга» (v1.0 §6) и «Человек» (v1.0 §1) | Один ID — разные объекты (C-05) |
| `OBJECT-TYPE-000003` | «Фильм» (spec §11), «Произведение» (v1.0 §4), «Веб-новела» (v1.0 §6) | Один ID — три объекта |
| `OBJECT-TYPE-000006` | «Контекст» (v1.0 §1) и «Человек» (v1.0 §4) | Один ID — два объекта |
| `OBJECT-TYPE-000000` | «Тип объекта» (spec §13) | Вне формата `000001` |
| `PROPERTY-000001` / `PROPERTY-TYPE-000001` | Свойство и тип свойства | Коллизия префиксов (C-08) |
| `CHARACTЕR` | Префикс типа «Персонаж» | Кириллическая «Е» (U+0415), омоглиф (C-06) |

**Почему класс этих ошибок устранён структурно.** ADR-0002 вводит ULID: идентификатор генерируется
локально, вероятностно уникален, не требует счётчика и не зависит от порядка создания. Присвоить
один ULID двум объектам практически невозможно, а правило `contract.r3` (уникальность `id` в хранилище)
обнаруживает нарушение как `error`. Правила `naming.r4…r6` и `naming.r9` закрывают омоглифы и коллизии
префиксов проверкой кодовых точек.

Следствие: C-04 и C-05 закрыты **не исправлением черновиков, а устранением порождающей их причины**.

## 4. Версии: документа и метамодели (C-41)

Черновик использовал одно поле `версия: 1.1-draft` одновременно для версии документа и версии модели.
В нашей документации поля разделены нормативно:

| Поле frontmatter | Что означает | Пример |
|---|---|---|
| `version` | версия **документа** | `0.3.0` |
| `metamodel_version` | версия **метамодели**, к которой документ относится | `0.11.0` |
| `status` | `draft` \| `review` \| `actual` \| `deprecated` \| `superseded` | `actual` |
| `superseded_by` | путь к заменяющему документу | `docs/adr/ADR-0005-classification.md` |
| `adr` | список ADR, которыми документ зафиксирован | `[ADR-0007, ADR-0011]` |

Версия метамодели — semver, правила повышения в `docs/templates/CHANGELOG_ENTRY_TEMPLATE.md`.
Версия плагина — отдельная, своя (семантически связана с `metamodel_version`, но не равна ей).

## 5. Служебные документы (C-37)

| Вопрос | Решение |
|---|---|
| Являются ли документы проекта объектами метамодели? | **Нет** (X-05). Документация проекта ≠ знание в базе |
| Нужен ли тип `Documentation`? | **Нет.** Тип исключён из ядра |
| Должны ли служебные документы иметь `id` в формате метамодели? | **Нет.** Они имеют `doc:` и `version:`, но не `id`-ULID и не `type` |
| Где живут? | В репозитории `docs/`, не в vault с данными |
| Что было не так в черновиках? | Все три файла имели `тип_объекта: документация` и `id: DOC-0000NN`, хотя тип не был определён ни в одном документе |
